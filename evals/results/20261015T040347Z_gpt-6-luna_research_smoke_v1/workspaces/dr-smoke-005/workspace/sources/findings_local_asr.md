# Findings: Local/On-Device ASR and TTS Architecture

## Scope
This note covers local/on-device speech architecture, focusing on offline operation, privacy boundaries, runtime/device constraints, and quality/latency trade-offs. It uses `whisper.cpp` as the primary implementation example and Android's `SpeechRecognizer` API as a platform-level boundary reference. It does not survey cloud speech APIs. TTS is addressed only as an architectural consideration; the sources retrieved here do not establish a specific local TTS implementation.

## Key Findings
- **Offline ASR is feasible when the model and runtime are locally available.** `whisper.cpp` is a C/C++ inference implementation of Whisper and supports running inference on local audio. Its repository describes CPU and hardware-accelerated paths, including Apple Silicon/Accelerate, AVX, CUDA, Vulkan, and other backends. This supports deployment without sending audio to a remote inference service, provided model acquisition, application updates, and any ancillary services are also handled locally or before offline use.
  Source: [whisper.cpp repository](https://github.com/ggml-org/whisper.cpp)
- **“On-device” is a data-flow property, not a guarantee implied by an API name.** Android's `SpeechRecognizer` reference includes an on-device recognizer creation API, but the platform API alone does not establish that every recognizer implementation, language pack, or configuration is available offline. Applications should explicitly check on-device availability and test behavior with network access disabled; otherwise a platform recognizer may have implementation-dependent service or model requirements.
  Source: [Android SpeechRecognizer API reference](https://developer.android.com/reference/android/speech/SpeechRecognizer)
- **Privacy boundaries include more than inference.** A local inference path can keep captured audio and transcripts on the device, but microphone permission, temporary audio buffers, logs, crash reports, backups, analytics, model downloads, and app-level synchronization remain separate potential egress paths. A privacy claim should specify which data stays local and whether any network activity occurs during model installation, updates, or operation.
  Evidence basis: local inference capability in the [whisper.cpp repository](https://github.com/ggml-org/whisper.cpp); the Android API reference documents a platform recognizer interface but does not by itself certify end-to-end data handling ([SpeechRecognizer](https://developer.android.com/reference/android/speech/SpeechRecognizer)).
- **Runtime constraints are device- and model-dependent.** Local ASR trades network dependence for local compute, memory, storage, energy, and thermal load. `whisper.cpp` exposes multiple hardware-specific acceleration options and quantized model support, indicating that model/runtime selection is a key deployment decision. Smaller or quantized models can reduce resource demands, but should be validated against the target device and accuracy requirements rather than assumed to preserve quality.
  Source: [whisper.cpp repository](https://github.com/ggml-org/whisper.cpp)
- **Latency depends on the full pipeline, not just model inference.** Capture buffering, voice activity detection/segmentation, model size, hardware backend, thread configuration, and whether results are streamed or emitted after a complete segment all affect perceived delay. Local execution avoids network round trips, but does not guarantee real-time performance on constrained devices. Benchmark end-to-end latency and sustained thermal behavior on representative hardware.
  Source: [whisper.cpp repository](https://github.com/ggml-org/whisper.cpp)
- **Quality and latency must be tuned together.** Recognition quality varies with model choice, language, acoustic conditions, and quantization; latency and memory generally improve with smaller models and optimized backends, potentially at a quality cost. Evaluate word/error metrics and user-perceived delay on representative speech, accents, noise, and device classes. For TTS, the same local-versus-remote boundary applies, but voice/model availability, package size, synthesis speed, and naturalness require separate evaluation; the sources retrieved do not substantiate a particular local TTS engine.

## Evidence and Uncertainty
The repository is a primary source for `whisper.cpp` capabilities, but its feature list is not a controlled benchmark and does not establish performance or accuracy on a particular device. The Android API reference is authoritative for the platform interface, but the fetched page output was truncated and does not provide enough evidence here to characterize all offline availability guarantees or data handling of recognizer implementations. No primary local-TTS source was retrieved, so TTS-specific implementation claims are intentionally limited. Device-specific latency, memory, battery, and quality conclusions require direct testing with the intended models and hardware.
