# Findings: SSE protocol and browser API for streaming LLM responses
## Research scope
This note covers Server-Sent Events (SSE) framing and the browser `EventSource` API as a transport for streaming LLM output, including request constraints, reconnection, event IDs, credentials, and practical implementation implications. It does not assess particular LLM providers or deployment stacks.

## Key findings
- **Normative framing:** An SSE response is UTF-8 text with media type `text/event-stream`. The stream is parsed as lines; a blank line dispatches the accumulated event. Fields include `data`, `event`, `id`, and `retry`; comments begin with `:` and can be used as keep-alives. Multiple `data:` lines are joined with newline characters. A stream ending without a terminating blank line does not dispatch the pending event. The W3C Recommendation is the primary source returned in search; it notes that the material is also in the WHATWG HTML specification.
  Source: [W3C Server-Sent Events Recommendation](https://www.w3.org/TR/2015/REC-eventsource-20150203/)
- **Browser API request constraints:** `EventSource` is constructed with a URL and optional `withCredentials` setting; it does not expose a method/body/custom-header option. Its connection is an HTTP GET, so native `EventSource` cannot directly submit a POST prompt or attach an `Authorization: Bearer ...` header. This is an API constraint, not a limitation of SSE framing itself. The returned MDN result is a Spanish API reference and the W3C spec is the normative source.
  Sources: [W3C Server-Sent Events Recommendation](https://www.w3.org/TR/2015/REC-eventsource-20150203/), [MDN EventSource API (Spanish)](https://developer.mozilla.org/es/docs/Web/API/EventSource)
- **Reconnect and `Last-Event-ID`:** Native EventSource reconnects after a connection ends unless closed by the client or the response indicates a non-retryable condition. The server may send `retry:` (milliseconds) to influence the reconnection delay. When an event has an `id:` field, the browser updates its last-event-ID state and sends it as the `Last-Event-ID` request header on reconnection. This supports resumption only if the application/server retains and replays events consistently; it does not itself guarantee exactly-once delivery or recover events the server no longer has.
  Source: [W3C Server-Sent Events Recommendation](https://www.w3.org/TR/2015/REC-eventsource-20150203/)
- **Credentials:** The API's `withCredentials` option controls whether a cross-origin EventSource request uses credentials under CORS; the default is false. Credentialed cross-origin use requires compatible server CORS response headers and cannot use wildcard `Access-Control-Allow-Origin` with credentials. Same-origin authentication can use browser-managed cookies. Because custom headers are unavailable, bearer-token authentication generally requires a different transport/client strategy or a carefully designed cookie/session approach; putting secrets in query strings risks exposure in logs and other URL-handling systems.
  Sources: [W3C Server-Sent Events Recommendation](https://www.w3.org/TR/2015/REC-eventsource-20150203/), [MDN EventSource API (Spanish)](https://developer.mozilla.org/es/docs/Web/API/EventSource)
- **Practical implications for LLM streaming:** For a simple browser stream, create a server-side generation/session resource with a GET-able stream URL, return `Content-Type: text/event-stream`, and emit each token/chunk as `data:` (often JSON-encoded), terminated by a blank line. Use explicit event names for lifecycle/error events and IDs only when the backend can replay from a cursor. Send periodic comment heartbeats where needed to keep intermediaries from treating an idle stream as dead. For POST-based prompt submission, custom authorization headers, request cancellation/control, or richer retry policy, use `fetch()` with a streaming response reader and parse SSE framing yourself, or use a library built on fetch. These are design recommendations; proxy buffering, idle timeouts, compression behavior, and connection limits vary by browser, network, and deployment and are not guaranteed by the SSE standard.
  Sources: [W3C Server-Sent Events Recommendation](https://www.w3.org/TR/2015/REC-eventsource-20150203/), [MDN EventSource API (Spanish)](https://developer.mozilla.org/es/docs/Web/API/EventSource)

## Evidence and uncertainty
The W3C Recommendation returned by search provides primary normative evidence for the event-stream format and EventSource behavior. The MDN result returned was the Spanish EventSource reference, which supports the API-level description but is not itself a standard. The WHATWG HTML page and English MDN pages were not returned as explicit search-result URLs, so they are not cited here. Search results did not provide primary evidence for deployment-specific proxy buffering, timeout, or browser connection-limit claims; these are therefore identified as environment-dependent rather than universal protocol facts. Exact operational behavior can depend on server, browser, CORS configuration, and intermediaries.
