# SSE vs. WebSockets for Streaming LLM Responses in Browser-Based AI Assistants

## Background

Browser-based AI assistants commonly need to display generated text incrementally rather than waiting for a complete response. The transport choice affects how the browser initiates a request, how messages are framed, whether the connection supports client-to-server messages, and how interruption and recovery are handled. This report compares the browser-native `EventSource` API for Server-Sent Events (SSE) with the browser WebSocket API, using standards and browser documentation as the primary evidence base.

The comparison is about transport capabilities, not a claim that either protocol is universally faster or cheaper. Provider-specific API behavior must be checked separately: the research run could not retrieve verifiable provider documentation text.

## Key Findings

- **SSE is a natural fit for one-way incremental output.** The WHATWG HTML standard defines an event-stream format and browser `EventSource` behavior, including automatic reconnection and `Last-Event-ID`. It is a server-to-browser event channel, not a bidirectional application messaging channel.
- **Native `EventSource` has important request-shape constraints.** It accepts a URL and optional credentials mode, but does not expose a general way to set a POST body or arbitrary request headers. If generation requires POST JSON or a custom authorization header, use a different request pattern—such as creating a generation first and subscribing to its URL—or use Fetch with a streaming SSE parser.
- **WebSockets provide bidirectional messaging on one connection.** This is useful when the browser must send control or interaction messages during generation. The application must define its own message schema, completion/error semantics, reconnection, and recovery behavior.
- **Neither protocol automatically provides application-level exactly-once generation recovery.** SSE reconnection and event IDs provide a possible cursor mechanism, but the server must persist and interpret events and the client must handle duplicates. WebSocket recovery is also application-defined.
- **The standard browser WebSocket API lacks receive-side backpressure.** Applications should bound queues and process messages promptly. The available evidence does not support a definitive comparison of SSE receive-side backpressure.
- **No universal performance winner is established.** Latency, throughput, cost, proxy behavior, and connection limits depend on implementation and deployment; the reviewed sources do not provide a controlled benchmark for LLM workloads.

## Evidence and Analysis

### Protocol and browser API comparison

| Dimension | SSE (`EventSource`) | WebSocket | Implication for an AI assistant |
|---|---|---|---|
| Directionality | Server-to-client event stream. | Bidirectional messages over one connection. | For submit-once/receive-many generation, SSE's directionality is often sufficient. For ongoing client controls or interactive messages during generation, WebSocket is more expressive. |
| Request initiation | Native `EventSource` connects by URL using GET; no request body or arbitrary headers ([WHATWG HTML](https://html.spec.whatwg.org/multipage/server-sent-events.html), [MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)). | Browser constructor establishes a WebSocket connection through an HTTP Upgrade handshake; the browser API does not provide a general arbitrary-header option ([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455), [MDN WebSocket constructor](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket)). | Neither native API should be assumed to support arbitrary bearer-header authentication. SSE is especially constrained when the generation request itself must be POSTed. |
| Framing | UTF-8 `text/event-stream`; fields such as `data`, `event`, `id`, and `retry`; blank line dispatches an event ([WHATWG HTML](https://html.spec.whatwg.org/multipage/server-sent-events.html)). | RFC 6455 defines frames and messages; application-level message semantics are not prescribed ([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)). | SSE supplies a standard text-event envelope. WebSocket requires an application protocol for deltas, completion, errors, cancellation, and metadata. A WebSocket frame is not inherently an LLM token. |
| Reconnection | EventSource reconnects after unexpected closure; `id`/`Last-Event-ID` can support a cursor ([WHATWG HTML](https://html.spec.whatwg.org/multipage/server-sent-events.html)). | Application must implement reconnection and recovery ([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)). | SSE offers a useful primitive, not durable delivery or resumable model execution. Both need explicit generation IDs, cursor semantics, and duplicate handling. |
| Flow control | The reviewed evidence does not establish a comparable receive-side backpressure guarantee for EventSource. | Traditional browser WebSocket API has no receive-side backpressure; excessive incoming messages can consume memory/CPU ([MDN WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket)). | For WebSocket, bound queues and consider chunk rate/size. Do not claim SSE is superior on backpressure without further evidence. |
| Operational path | HTTP event stream; correct `Content-Type` and incremental flushing matter; intermediaries may buffer ([WHATWG HTML](https://html.spec.whatwg.org/multipage/server-sent-events.html), [MDN Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)). | Long-lived upgraded connection; lifecycle, timeouts, and intermediary support need validation ([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)). | Test the actual proxy/load-balancer/CDN path. Protocol choice alone does not guarantee prompt token delivery. |
| Security and credentials | Cross-origin access follows CORS; credentials require explicit configuration and compatible response headers. Third-party cookie policies may still prevent cookies from being sent ([MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/CORS), [MDN EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)). | Server can validate the handshake `Origin`; use `wss:` for TLS ([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)). | Design authentication and origin checks deliberately. Origin validation is not user authentication, and browser APIs constrain custom headers. |

### Trade-offs and suitable scenarios

**SSE advantages:** a standard event framing model, a browser-native subscription API, and built-in reconnection behavior with an event-ID cursor. It is a good fit when the browser primarily receives incremental output and the server can expose a stream URL. Its main native-API drawback is the GET-only request shape and lack of arbitrary headers/body.

**WebSocket advantages:** a single persistent bidirectional channel can carry generated output and client control messages. This can simplify products with ongoing interactive sessions or frequent in-generation controls. The cost is more application-level protocol and lifecycle work: message types, authentication, reconnect/backoff, resume cursors, duplicate handling, and receive-load management.

**Practical middle ground:** if the model request needs POST JSON or custom headers but the response is one-way, a browser can issue a Fetch request and parse a streaming response using SSE framing (or another documented stream format). This is an optional architecture pattern, not a requirement of either standard; it preserves an HTTP request shape suitable for generation without requiring a bidirectional WebSocket. It is not the native `EventSource` API and requires explicit stream parsing and cancellation handling. Another option is to create a generation task and then subscribe to its URL, but avoid putting sensitive prompts or credentials in URLs and account for URL length and exposure in logs/history.

### Evidence basis

The normative SSE behavior is described by the [WHATWG HTML Server-sent events specification](https://html.spec.whatwg.org/multipage/server-sent-events.html); browser-facing details are documented by [MDN: Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events), [MDN: EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource), and [MDN: CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/CORS). WebSocket protocol behavior is specified in [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455), with browser API behavior documented by [MDN: WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket) and [MDN: WebSocket constructor](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket).

The research attempted to verify official LLM provider streaming documentation, including OpenAI documentation, but did not retrieve page text. Candidate official URLs were recorded in the findings, but their current contents were not verified. Therefore, this report does not attribute a transport, event schema, or browser recommendation to any specific provider.

## Recommendations

1. **As a general browser-transport recommendation, prefer SSE (or Fetch-parsed SSE) for ordinary one-way token streaming** when the interaction is primarily one request followed by server-to-browser deltas. This is not a claim that any particular LLM provider supports or recommends SSE. Prefer native `EventSource` only when a URL-based GET subscription and its credential model fit the API.
2. **Use Fetch streaming with SSE parsing** when the request needs POST JSON, custom headers, or explicit request cancellation while the response remains one-way. Define event parsing and error handling carefully; do not treat arbitrary network chunks as complete events.
3. **Choose WebSockets when bidirectionality is a product requirement**, such as sending ongoing control messages or interactive session events over the same connection. Before adoption, specify message types, cancellation, completion/error signaling, reconnect/backoff, resume behavior, authentication, and bounded client queues.
4. **For either transport, design recovery explicitly.** Give each generation a stable identifier; decide whether reconnect resumes, restarts, or fails; define event/message sequence IDs and duplicate handling; and ensure cancellation reaches the generation backend.
5. **Validate deployment behavior end to end.** Test incremental flushing, proxy buffering, idle timeouts, cross-origin credentials, TLS, and browser behavior in the actual production path. Do not select based on unsupported assumptions about universal latency or cost superiority.

## Limitations

- Provider-specific official documentation was not retrieved as verifiable page text. The report therefore cannot confirm any particular LLM API's current transport, event names, payload schema, browser support, or provider-specific caveats. The candidate OpenAI documentation URLs in the research notes are not treated as verified evidence.
- The standards and MDN pages are linked as primary/technical references, but the search service returned quota/403 errors and their page text was not independently fetched during this run. Link inclusion should not be read as independent verification of current page contents; the report relies on the standard/API facts captured in the findings. Readers should verify current documentation before implementation.
- No controlled benchmark was found for latency, throughput, cost, or resource use under representative LLM workloads. These outcomes depend on server implementation, chunking, network path, proxies, and client processing.
- Proxy buffering, idle timeouts, browser cookie policies, connection limits, and authentication deployment are environment-dependent. SSE event IDs do not guarantee durable or exactly-once delivery, and WebSocket does not provide application-level resume semantics by itself.
- The comparison concerns the traditional browser `WebSocket` API and native `EventSource`; other APIs, libraries, and server-side clients may have different flow-control or request capabilities.
