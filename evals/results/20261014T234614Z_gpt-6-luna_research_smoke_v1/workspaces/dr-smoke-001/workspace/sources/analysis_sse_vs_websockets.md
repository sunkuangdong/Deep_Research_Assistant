## 分析结论

### 分析维度与关键比较

| 维度 | SSE（原生 `EventSource`） | WebSocket（浏览器标准 API） | 对浏览器 LLM 助手的含义 |
|---|---|---|---|
| 方向性 | 服务端向客户端推送事件；原生 EventSource 连接由浏览器以 GET 建立，接口不提供客户端在同一连接发送应用消息的能力。 | 单条连接支持双向通信；客户端可发送消息，服务端可连续返回消息。 | 若交互主要是提交一次生成请求、随后接收增量输出，单向推送通常足够；若同一连接还需频繁发送取消、控制或其他实时消息，WebSocket 的双向通道更贴合，但应用协议仍须自行定义。 |
| 浏览器 API / 请求约束 | `EventSource` 构造参数为 URL 与可选 `withCredentials`；不能配置 POST、请求体或任意请求头。跨源凭据需显式启用并满足 CORS。 | 浏览器构造器建立 WebSocket 连接，但不提供通用的任意握手请求头设置参数；连接建立后可用 `send()` 发送应用数据。 | 若生成请求必须携带 POST body 或自定义 Authorization 头，原生 EventSource 不适配直接发起该请求；可考虑先创建任务再订阅 URL，或用可控的 Fetch 流解析。WebSocket 也不能假定可在浏览器握手中任意设置认证头，认证需另行设计。 |
| framing / 消息边界 | UTF-8 `text/event-stream`，按行解析；空行触发事件派发，字段包括 `data`、`event`、`id`、`retry`。 | RFC 定义帧与消息；消息可跨多个帧，浏览器通常向应用交付重组后的消息事件。LLM chunk/token 边界由应用层协议定义。 | SSE 自带文本事件 framing；WebSocket 提供消息传输但不规定 LLM 事件格式。两者都需要明确增量内容、完成、错误及取消等应用语义，不能把网络帧直接等同于 token。 |
| 重连 / 恢复 | EventSource 在连接意外关闭后自动重连；`retry:` 可影响等待时间，`id:` 与重连请求中的 `Last-Event-ID` 可提供恢复游标。它不保证应用层 exactly-once，也不自动提供事件持久化或任务恢复。 | 协议/浏览器 API 不提供应用级自动重连与断线续传保证；应用需处理生命周期事件并自行实现重连、游标和未完成任务策略。 | SSE 有内建重连机制，但仍需服务端保存/解释游标并处理重复；WebSocket 的恢复逻辑完全由应用设计。一次性生成尤其要避免重连后重复启动或重复展示输出。 |
| 背压 | 指定材料未提供足以比较原生 EventSource 接收侧背压能力的明确依据；不据此断言其具备或不具备某种流控接口。 | 传统浏览器 WebSocket API 没有接收端背压接口；消息处理落后可能造成内存增长或 CPU 饱和。`bufferedAmount` 反映发送侧排队字节，不是接收侧流控。 | WebSocket 接收端需在应用层控制消息速率、队列和处理负载。SSE 的接收侧流控能力在现有材料中证据不足，需避免作无依据的优劣判断。 |
| 安全 / 认证 | 跨源访问受 CORS 约束；凭据模式需 `withCredentials: true`，服务端需匹配的允许来源及允许凭据响应头，凭据模式不能使用 `Access-Control-Allow-Origin: *`。第三方 Cookie 策略仍可能影响 Cookie。原生接口不能任意添加请求头。 | 握手包含 `Origin`，服务器可据此校验浏览器来源；`wss:` 可使用 TLS。浏览器 API 不提供通用自定义握手头设置，认证需结合 Cookie/会话或应用层机制设计。 | 两者都不能简单假设浏览器可任意附加 Bearer 头。应按部署环境设计认证、来源校验、凭据策略与 TLS；SSE 还需正确配置 CORS。不要把 Origin 校验等同于完整身份认证。 |
| 运维与部署适配 | 基于 HTTP 事件流；服务端需正确设置 `text/event-stream`，逐步输出完整事件并以空行结束，避免代理/中间层缓冲。可利用事件 ID 设计恢复，但需应用端持久化与游标逻辑。 | 通过 HTTP Upgrade 建立长连接；需处理连接生命周期、关闭、异常断开及应用级重连。代理/负载均衡器超时、消息尺寸等依赖实现和配置。 | SSE 的事件格式与 HTTP 交付路径适合简单的单向增量输出，但仍需验证缓冲与超时配置。WebSocket 适合需要持续双向会话的系统，但需承担连接管理和应用协议运维。现有材料不足以量化两者的吞吐、延迟或成本差异。 |
| 适用场景（建议） | 推荐用于浏览器以 URL 订阅、主要接收服务端增量文本、请求可通过 GET/预先创建任务表达，且希望采用标准事件格式与内建重连行为的场景。若需 POST body/自定义头，可用 Fetch 流解析 SSE 或调整请求流程。 | 推荐用于同一连接需要双向实时消息（例如生成期间持续发送控制/取消消息或多类交互）的场景，并且团队愿意实现应用层 framing、重连、恢复、认证与流控策略。 | 这是基于通用能力的架构建议，不是提供方兼容性结论。具体选择还取决于 API 请求形态、认证方式、恢复语义、部署链路及客户端负载。 |

### 标准支持事实与建议的区分

**标准/浏览器文档支持的事实（按现有 findings 摘要）：**
- WHATWG/MDN 所述原生 EventSource 使用 URL 与可选凭据模式，浏览器连接为 GET；接口不提供请求体或任意请求头配置。
- SSE 事件流使用 `text/event-stream`，按 UTF-8 文本行解析，空行触发事件派发；支持 `id`、`retry` 等字段及 `Last-Event-ID` 重连机制。
- RFC 6455 定义 WebSocket 双向通信、握手、帧/消息及关闭控制；浏览器 API 通过 `send()` 与 `message` 事件收发应用数据。
- 传统浏览器 WebSocket API 没有接收端背压接口；发送侧 `bufferedAmount` 不是接收侧流控。
- WebSocket 的应用级重连/续传语义不由协议保证；SSE 的重连也不等于应用层无重复、无丢失保证。

**架构建议（由上述事实推导，不是标准强制要求）：**
- 以单向生成输出为主时，优先评估 SSE；若请求必须 POST 或带自定义头，考虑 Fetch 流解析 SSE、先创建任务再订阅，或其他适配方式。
- 需要同一连接双向控制时，评估 WebSocket，并明确应用消息格式、取消、完成/错误、重连游标、重复处理、队列上限与认证方案。
- 无论选择哪种传输，都应端到端验证代理缓冲、连接超时、跨源策略、凭据行为及断线恢复；不要仅凭协议名称推断部署表现。

### 明确结论

对于典型的浏览器 AI 助手“提交生成请求后接收单向增量文本”模式，**优先考虑 SSE（或由 Fetch 发起并解析 SSE）**：其事件 framing 与单向推送相匹配，且 EventSource 提供自动重连和事件 ID 游标机制；但原生 EventSource 的 GET、无请求体/自定义头限制，以及应用仍需实现可靠恢复，必须纳入设计。若产品需要在生成过程中通过同一连接持续双向发送控制或交互消息，**WebSocket 更合适**，前提是应用自行承担消息协议、重连/恢复、接收负载控制和认证设计。现有材料不支持宣称某一方案在性能、成本或所有部署环境中普遍更优。

**提供方文档限制：provider-specific official docs were not retrieved。** 指定的提供方 findings 明确记录未取得可核验的官方文档正文，因此本分析不能确认任何特定 LLM 提供方当前支持/推荐的传输方式、事件名称、载荷格式、浏览器集成方式或 caveat；上述结论仅针对通用标准与浏览器 API 行为。

## 数据缺口与不确定性

- 提供方官方文档未检索/读取成功；不能把通用 SSE 或 WebSocket 行为归因于特定 API 或 SDK。
- findings 中的标准与 MDN 内容未在本次分析中重新核验页面版本；分析仅复述现有材料。
- SSE 接收侧背压在现有材料中没有足够证据，故未作与 WebSocket 的确定性比较。
- 代理缓冲、连接超时、最大消息尺寸、浏览器差异、第三方 Cookie 策略及具体认证部署均可能影响实际表现；现有材料未提供可量化的对照数据。
- SSE 的 Last-Event-ID 只是恢复游标机制，不自动保证事件持久化、无重复/无丢失或 LLM 生成任务可续跑；WebSocket 同样需要应用层恢复语义。
