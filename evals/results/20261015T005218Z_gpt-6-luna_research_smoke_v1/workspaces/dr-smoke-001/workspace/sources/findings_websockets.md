# Findings: WebSocket Protocol and Browser Behavior for Streaming LLM Responses

## Research scope
This file covers only the WebSocket protocol and browser behavior relevant to streaming LLM responses: bidirectional framing, the browser WebSocket API, connection lifecycle and reconnect behavior, authentication/security, and operational implications. It does not cover alternative streaming transports.

## Key findings
- **WebSocket is a bidirectional, message-oriented protocol over a persistent connection.** RFC 6455 defines a client-initiated opening handshake followed by framed data in both directions. Frames carry text or binary data; fragmentation can split a message across frames, and control frames (including Ping, Pong, and Close) have protocol-defined roles. Browser JavaScript receives complete messages through `message` events rather than direct access to individual wire frames. For LLM output, the application must define its own message/event schema and decide how to represent token deltas, completion, errors, and metadata.
  Source: [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)
- **Browser API is event-driven and exposes a small surface.** A page creates a connection with `new WebSocket(url[, protocols])`, observes `open`, `message`, `error`, and `close`, sends with `send()`, and requests closure with `close()`. `readyState` distinguishes CONNECTING, OPEN, CLOSING, and CLOSED; `bufferedAmount` reports queued outbound bytes. The browser API does not expose raw frame construction, protocol Ping/Pong controls, or a built-in backpressure/stream reader interface. Applications should avoid unbounded outbound queues and use application-level flow control where needed. Incoming messages are delivered as message events; large or frequent streams still require application-side parsing, rendering throttling, and memory management.
  Sources: [WHATWG WebSockets Standard](https://html.spec.whatwg.org/multipage/web-sockets.html), [MDN WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket)
- **Lifecycle is not equivalent to a durable session.** A connection can fail because of network loss, server/proxy timeout, browser shutdown, or explicit close. The `close` event provides a close code, reason, and cleanliness indicator, but a transport close does not establish whether the server completed the LLM generation or whether the client received every emitted update. A robust application needs request/generation identifiers, explicit terminal events, and a way to reconcile state after interruption.
  Sources: [WHATWG WebSockets Standard](https://html.spec.whatwg.org/multipage/web-sockets.html), [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)
- **The browser WebSocket API does not automatically reconnect.** Reconnection, retry timing, duplicate suppression, and resumption are application responsibilities. A reconnect creates a new connection; it does not by itself restore prior subscriptions, replay missed messages, or resume a generation. For LLM streaming, define whether retry means restarting generation, querying status, or resuming from a sequence/cursor, and make retries idempotent where possible. Use bounded exponential backoff with jitter and distinguish transient failures from authorization/protocol failures.
  Sources: [WHATWG WebSockets Standard](https://html.spec.whatwg.org/multipage/web-sockets.html), [MDN WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket)
- **Authentication and security require explicit design.** The browser constructor accepts a URL and optional subprotocols, not arbitrary request headers, which constrains common bearer-token header patterns. Browser deployments commonly rely on secure `wss:` plus same-site/session cookies or a short-lived credential in the URL/subprotocol, but URL credentials can leak through logs and telemetry and should be avoided or tightly scoped. RFC 6455 defines the `Origin` handshake field for browser-origin checks; servers should validate allowed origins and authenticate/authorize each connection and requested operation. Cookie-authenticated sockets need defenses against Cross-Site WebSocket Hijacking (including strict origin validation and appropriate cookie policy). Use `wss:` in production, validate message sizes and schemas, rate-limit, and avoid treating an established socket as authorization for every action indefinitely.
  Sources: [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455), [WHATWG WebSockets Standard](https://html.spec.whatwg.org/multipage/web-sockets.html), [MDN WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket)
- **Operational implications for LLM streaming:** persistent connections consume server and intermediary connection capacity; idle timeouts and network changes can terminate them, so heartbeat/timeout policy must be coordinated with infrastructure. Browser JavaScript cannot send protocol-level Ping frames directly, so application-level heartbeat messages may be needed if the service requires client-originated liveness checks. Keepalive behavior and proxy timeout values are deployment-specific. Stream messages should be bounded and structured; server-side flow control and client rendering throttling help prevent slow consumers from accumulating work. Treat delivery as potentially interrupted rather than assuming exactly-once delivery.
  Sources: [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455), [WHATWG WebSockets Standard](https://html.spec.whatwg.org/multipage/web-sockets.html)

## Evidence and uncertainty
The protocol-level claims are grounded in RFC 6455, and browser API behavior in the WHATWG standard; MDN is included as a secondary explanatory reference. The search results available in this run did not return the primary-source pages themselves, so the source URLs are provided for verification and the findings reflect the standards/API behavior rather than quoted search snippets. Operational recommendations (heartbeat intervals, retry policy, replay/resumption, and capacity planning) depend on the application, server implementation, and proxy/load-balancer configuration; WebSocket itself does not prescribe a universal reconnect or LLM-stream recovery policy. Browser support details and evolving API behavior should be checked against current implementations when making compatibility decisions.
