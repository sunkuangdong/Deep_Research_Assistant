# 实时语音 Agent 端到端架构：调研报告

## 背景

实时语音 Agent 的体验由一条连续链路共同决定：麦克风音频进入传输与识别层，ASR 逐步产出文本，LLM 生成响应，TTS 合成音频并交给客户端播放。与离线语音处理不同，实时系统必须在结果尚未完整时持续推进，同时允许用户随时插话。因此，端到端设计的关键不只是单个模型的速度，而是流式边界、状态归属、缓冲策略和取消路径能否协同。

本报告依据本轮检索到的标准组织及厂商官方文档，分析媒体传输、流式 ASR、生成/播放状态、打断处理、音频缓冲与会话状态。文档证据主要说明协议和 API 行为，不构成特定部署的性能基准。

## 关键发现

1. **流式链路应分层，媒体面、信令面与应用会话控制面不可混为一谈。** WebRTC 以 RTP/RTCP 承载媒体并提供反馈与监测机制；W3C WebRTC API 涵盖连接协商、ICE 等接口，但应用信令并非完整由 WebRTC 规范定义。传输连接状态不能代替对话轮次状态。
2. **ASR 中间结果与最终结果语义不同。** Azure 文档区分 `recognizing` 中间结果和 `recognized` 最终结果；Google 流式识别持续接收音频并返回识别文本。中间结果适合低延迟预览，但应允许修订；最终结果更适合作为稳定输入。静音分段与语义分段存在响应速度和片段完整性的取舍。
3. **打断必须跨层传播，而非只停止扬声器。** 用户插话时，系统需要协调生成取消、停止后续音频、清理旧轮次播放队列并更新会话状态。现有官方证据未核实特定 Realtime API 的取消事件语义，因此这是架构建议，不是某个 API 的保证。
4. **生成状态、播放状态和会话/轮次状态应独立建模。** 模型停止生成不代表客户端已播完；播放队列清空也不必然意味着轮次已提交。建议用轮次标识关联识别、生成和音频片段，避免旧响应残留。
5. **缓冲是连续性与可打断性的权衡点。** 较小分块可能更早开始播放，但增加调度与传输开销；较大缓冲有助于连续播放，却可能增加打断后的尾音。现有材料没有可靠的分块大小、缓冲时长或端到端延迟数据，参数必须实测。

## 证据与分析

### 端到端职责与状态边界

| 层次 | 主要职责 | 设计要点与取舍 |
|---|---|---|
| 媒体传输与连接 | 双向音频承载、连接协商、网络反馈与传输监测 | RFC 8834 描述 RTP/RTCP、丢包鲁棒性、拥塞控制和性能监测；W3C WebRTC 提供浏览器侧连接/API。[RFC 8834](https://www.rfc-editor.org/rfc/rfc8834.html)；[W3C WebRTC 1.0](https://www.w3.org/TR/webrtc/)。重传或纠错可改善鲁棒性，但恢复等待可能与及时播放冲突。不能仅凭使用 WebRTC 推断直连或特定时延。 |
| 流式 ASR | 接收音频流，产出中间/最终文本及分段信号 | Google Cloud Speech-to-Text 流式识别文档说明该服务接口通过 gRPC 提供，单条音频消息上限为 25 KB；该限制是该服务的消息约束，不是延迟指标。[Google Cloud 文档](https://docs.cloud.google.com/speech-to-text/docs/streaming-recognize)。Azure 连续识别文档区分中间与最终结果，并指出静音分段可能欠分段或过度分段。[Microsoft Learn 文档](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/how-to-recognize-speech)。 |
| LLM 与会话控制 | 根据已提交输入生成响应，维护轮次与取消状态 | 本轮 OpenAI Realtime 官方页面抓取内容不足以核实具体事件、状态转换或取消语义。应用层应显式维护轮次 ID 和生成任务状态，避免把推论误当 API 行为。 |
| TTS 与播放 | 将响应转为音频片段并管理播放队列/进度 | 本轮未取得可引用的 TTS 流式官方页面证据，无法确认具体分块、缓冲或取消能力。播放队列可清空、按轮次隔离属于通用架构建议，需按目标 API 验证。 |
| 打断控制 | 将用户插话传播到生成、合成、队列和会话状态 | 只停止客户端播放可能留下后台生成；只取消生成也可能让已缓冲音频继续播放。应把打断设计为跨层控制事务，并记录各层完成/取消状态。 |

### 流式传输与增量识别

WebRTC 的媒体传输与应用信令应分开设计：信令负责交换连接协商信息，媒体面负责实时音频传输；RTCP 反馈和统计可用于观察网络质量。传输层的丢包恢复、拥塞适配等机制解决的是网络鲁棒性，不负责判断用户话语是否结束或当前对话轮次是否有效。

ASR 的中间结果可让系统更早准备响应，但可能被后续识别修订；若过早将其当作最终意图，可能触发错误或重复响应。等待最终结果或更完整的语义分段有利于稳定性，却可能增加响应等待。适合的策略取决于交互类型：短命令可偏向快速端点，开放式对话则应避免仅凭短暂停顿切断语义。现有文档没有可直接比较的延迟或准确率基准，不能据此给厂商或策略做性能排名。

### 打断、缓冲与会话状态

建议将状态至少拆分为：连接状态、输入/语音活动状态、ASR 中间与最终结果状态、对话轮次状态、模型生成状态、TTS/播放状态，以及取消/过期状态。每个响应和音频片段携带轮次标识；新轮次开始或旧轮次被打断时，控制器可据此取消生成并丢弃过期片段。

打断路径应覆盖“停止生成—停止后续合成/发送—清理播放队列—更新轮次状态”，并通过事件时间戳验证各环节是否真正完成。缓冲队列深度、播放进度、ASR 最终化时间、生成开始/结束时间和打断到静音的尾音时间，都是建议采集的端到端观测指标；本轮来源没有给出这些指标的目标阈值。

### 量化证据与不确定性

现有 findings 没有可用于端到端比较的可靠量化数据，因此不进行延迟、准确率、缓冲时长或性能排名计算。可确认的数值仅包括 Google Cloud Speech-to-Text 流式识别文档所述的单条音频消息 25 KB 限制，以及 Azure 单次识别模式在末尾静音或最多处理 15 秒音频后结束的文档描述；这些是各自服务/模式的接口或行为约束，不应误读为普遍适用的系统约束或性能指标。

主要证据缺口包括：OpenAI Realtime 具体事件与取消语义未核实；TTS 流式分块和缓冲官方证据不足；Google ASR 语音活动事件的具体参数未展开；不同服务的端到端延迟、首音时间、词错率和打断尾音没有可比数据。因此，状态拆分、队列清理和跨层取消属于基于职责边界的架构推论，需在目标实现中验证。

## 建议

1. **先定义应用层状态机。** 明确连接、输入识别、轮次提交、生成、播放、取消和完成的状态及转换；不要用单一“会话完成”标志覆盖所有阶段。
2. **为每轮对话建立唯一标识。** 将 ASR 结果、LLM 响应、TTS 音频片段和播放队列项关联到轮次，支持取消后丢弃旧轮次内容。
3. **把打断实现为跨层事务。** 用户插话时同时触发生成取消、停止后续音频、清理播放队列和状态更新；针对目标 API 验证取消是否可中断、是否有已发送音频无法撤回等边界。
4. **区分中间识别与最终提交。** 中间结果可用于预热或可撤销的响应准备；只有在明确的端点/提交策略后，才将文本作为稳定轮次输入。避免把静音边界机械等同于语义边界。
5. **以实测调优缓冲和分块。** 在目标网络、设备、语言和 API 上测量首音时间、队列深度、连续播放中断率、打断到静音时间及识别最终化时间，再选择缓冲策略；不要从通用文档推导固定参数。
6. **建立分层可观测性。** 同时记录 RTP/RTCP 或连接统计、ASR 中间/最终事件、生成生命周期、音频入队/播放/清空和打断传播时间，便于区分网络问题、识别等待与播放尾音。

## 局限性

本报告基于本轮成功检索或抓取并记录在 findings 中的官方页面。传输与 ASR 证据较明确，但 OpenAI Realtime 页面正文未能支持具体事件语义，TTS 流式官方页面未成功核验；因此相关实现建议不能视为厂商 API 保证。规范和产品文档也不提供统一的端到端性能基准，实际表现会受网络、设备、语言、模型、配置和客户端播放实现影响。报告未进行实机测试或跨服务基准测试。
