# 企业 AI Agent 平台可靠性架构：状态、队列、幂等与恢复

## 背景

企业 AI Agent 不只是一次模型请求：它可能连续调用多个工具、运行数小时或更久、等待人工审批，并在 Worker 重启、网络超时或外部 API 返回不确定时继续执行。设计重点不是追求抽象的“恰好一次”，而是让流程状态可持久恢复、任务可重新分发、外部副作用可安全重试，并能审计每次决策与审批。

本报告依据本轮核验的官方文档，讨论持久化工作流状态、队列职责、幂等性、人工审批和故障恢复。队列产品的官方语义证据未能充分取得，因此相关建议以通用架构原则表述，不对 SQS 或 Kafka 的具体行为作未经核验的断言。

## 关键发现

1. **持久化工作流状态应是业务进度的事实来源，而非 Worker 内存或队列消息。** Temporal 以持久化事件历史恢复 Workflow Execution；LangGraph 通过 checkpointer 保存中断状态，并以同一 `thread_id` 恢复。队列适合唤醒和分发工作，不应单独承担业务状态账本。
2. **恢复/重放可能再次运行步骤，不能假设外部副作用自动回滚或只发生一次。** LangGraph 明确指出恢复时中断节点从头执行；Temporal 依赖事件历史重放。外部工具调用应有稳定业务操作 ID、幂等键和业务侧去重记录，并对结果不确定的调用进行查询或对账。
3. **人工审批应建模为持久化的暂停状态和显式恢复事件。** 保存待审批动作摘要、审批人/权限、业务操作 ID、工作流 ID、有效期和决定；审批通过后恢复流程，再执行不可逆副作用。超时、撤销、拒绝和过期授权需由应用定义。
4. **工作流级执行语义不等于跨系统端到端 exactly-once。** AWS Step Functions 的 Standard 与 Express 执行语义不同；即使工作流引擎提供特定执行保证，外部系统的副作用仍需独立幂等与对账设计。
5. **本轮队列官方证据不足。** 未核验到可用于支撑 SQS/Kafka 确认、重投递、可见性超时等机制的相关官方页面；因此不作产品级比较，也不以无关搜索结果充当技术来源。

## 证据与分析

### 状态存储与恢复

Temporal 的 Workflow Execution 通过持久化事件历史保存进度，Worker 可在故障后重放历史恢复状态；Worker 缓存只是性能优化，不是持久化事实来源。[Temporal Workflow Execution overview](https://docs.temporal.io/workflow-execution) 这支持将业务流程状态与执行进程生命周期解耦：Worker 可以替换，流程仍可从已记录的边界继续。重放要求历史与工作流逻辑保持兼容；本轮未进一步核验 Temporal 确定性约束的完整细节，实施时应按所选版本的官方指南验证。

LangGraph 的 `interrupt()` 可暂停执行并由 checkpointer 保存状态，之后使用同一 `thread_id` 和 `Command(resume=...)` 恢复。[LangGraph：Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) 这说明审批等待应作为持久化工作流状态，而不是让进程挂起或仅在内存中保存待办。恢复时节点从头执行，故暂停点之前的代码也可能再次运行。

AWS Step Functions 文档区分 Standard 与 Express：前者面向长时执行并提供执行历史，后者执行时长较短且采用 at-least-once 语义；其 Retry/Catch 可表达错误路径。[What is Step Functions?](https://docs.aws.amazon.com/step-functions/latest/dg/welcome.html) 这可作为按任务时长、审计需求和重复执行容忍度选择执行模型的参考，但不能把工作流级语义扩大解释为外部工具调用的端到端保证。

### 队列与任务分发

队列与工作流引擎应分工：队列负责异步唤醒、负载缓冲和 Worker 分发；持久化工作流/业务存储负责任务状态、步骤进度、审批状态和最终结果。消费者应以任务 ID 或业务操作 ID 识别重复处理，并在处理状态与副作用之间设计可恢复边界。

但本轮没有取得可核验的 SQS 或 Kafka 官方队列语义页面，无法可靠说明具体确认协议、重投递条件、可见性超时、死信处理或交付保证。上述分层是架构建议，不是对某个队列产品的事实陈述。选型和配置前必须核对目标产品官方文档，并通过故障注入验证消费者崩溃、确认丢失、重复投递和积压恢复行为。

### 幂等性与工具副作用

Stripe 的 API 文档说明幂等键可用于安全重试，并对同一键复用首次请求结果；但键有保留期限，不能替代应用自己的长期业务去重账本。[Stripe：Idempotent requests](https://docs.stripe.com/api/idempotent_requests) findings 指出该页面抓取正文有限，因此具体保留期和缓存行为的可见证据有限，实施时应核对目标 API 的当前官方说明。由此推导，平台应为每个逻辑副作用生成稳定操作 ID，将其与工具名称、参数摘要、调用状态、外部响应和重试次数持久化；同一逻辑操作的重试复用同一幂等键。若外部 API 不支持幂等键，则需在平台侧建立唯一约束/去重记录，并在结果不确定时先查询外部状态或进入人工核查，避免盲目重试。

幂等键只约束特定 API 的重复请求，不等于工作流状态恢复；反过来，checkpoint 也不能阻止外部系统重复产生效果。两者必须组合，并明确键的作用域、参数一致性、保留期和过期后的保护策略。

### 人工审批与故障恢复

审批记录应与工作流线程和业务操作建立稳定关联，至少保存：操作 ID、工作流/线程 ID、待执行动作及参数摘要、审批状态、审批人身份与权限依据、决定时间、有效期、审计记录。恢复前重新校验审批对象与待执行操作一致，拒绝过期或错配的决定。审批通过后再执行不可逆动作；若业务要求审批前先执行准备步骤，应确保该步骤只读或幂等。

故障恢复应区分“恢复流程控制状态”和“恢复外部世界状态”。Worker 崩溃可由持久化历史/checkpoint 恢复；外部 API 已成功但响应丢失时，流程状态可能仍显示未知。此时应使用幂等键重试、查询外部结果、对账或补偿，而不是假设重放会撤销或自动识别副作用。对无法安全自动恢复的情况，应进入人工核查队列并保留完整审计轨迹。

### 架构取舍

以下为基于已核验机制的通用设计推论，并非所列产品文档对具体实现的直接承诺；outbox、状态字段、消费者处理顺序等细节须结合目标数据库、队列和工作流产品官方文档验证。

- **事件历史/持久化工作流**：适合长时、多步骤、需审计和故障后续跑的任务；代价是需要管理历史增长、版本兼容和工作流逻辑约束。
- **队列驱动的短任务**：适合高并发、可拆分、可重试的工作单元；但队列本身不应成为业务状态唯一来源，且具体交付语义必须按产品核验。
- **业务侧幂等账本**：增加存储与状态管理成本，但能覆盖第三方幂等键过期、工具不支持幂等键及跨步骤重复调用等风险。
- **审批后执行副作用**：降低未授权或重复动作风险，但会增加端到端时延，并要求审批超时、撤销、升级和恢复策略。

## 建议

1. **采用分层持久化模型。** 工作流引擎保存执行历史/检查点；业务数据库保存任务、审批、工具调用和幂等账本；队列只承担分发与唤醒。可评估事务性 outbox 或等效机制协调业务状态提交与消息发布，避免双写缺口；这是通用设计推论，具体实现需结合所选数据库和队列验证。
2. **定义明确的任务状态机。** 至少区分 `queued`、`running`、`waiting_approval`、`retry_wait`、`succeeded`、`failed`、`cancelled`、`needs_reconciliation`。每次状态迁移记录版本、时间、原因和关联操作 ID；使用条件更新/乐观并发控制防止过期 Worker 覆盖新状态。该状态集合是建议的应用模型，不是来源文档规定。
3. **将工具调用封装为可恢复的副作用步骤。** 每个逻辑动作生成稳定 `operation_id`，持久化请求摘要和结果；支持时传递稳定幂等键。对超时但结果未知的调用先查询或对账；对不支持幂等的工具设置业务侧唯一约束、人工核查或补偿路径。
4. **把审批作为持久化等待状态。** 保存审批上下文和有效期，审批决定作为独立、可审计事件写入；恢复时校验身份、权限、操作摘要和有效期。拒绝、撤销、超时和审批人变更都应有明确状态迁移。
5. **设计队列消费者为可重入。** 以任务/操作 ID 去重，持久化领取/处理状态，再执行可控步骤；处理完成后再确认消息。由于本轮未核验具体队列语义，确认顺序、租约/可见性超时、死信和重试策略必须按目标产品官方文档确定，并用崩溃注入测试验证。此处顺序是设计建议，不是对特定队列协议的断言。
6. **建立恢复与补偿运行手册。** 覆盖 Worker 崩溃、重复投递、外部调用响应丢失、审批长期等待、状态与外部系统不一致、队列积压等场景；定义自动重试上限、退避、告警、人工接管、对账和补偿流程。
7. **用故障注入验证端到端语义。** 在工具调用前后、状态提交前后、消息确认前后、审批恢复前后注入崩溃和网络超时，验证不会丢任务、重复产生不可逆效果或绕过审批。将“至少一次投递 + 幂等处理”作为默认防御思路，而非依赖未经验证的 exactly-once 假设。
