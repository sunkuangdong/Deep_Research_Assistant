# 企业 AI Agent 上线前评估体系与发布门槛

## 背景

企业 AI Agent 的质量不只取决于最终回答，还取决于任务是否完成、工具选择与参数是否正确、执行轨迹是否符合预期，以及部署后服务和依赖是否稳定。单一离线分数无法覆盖真实运行环境；单次 Smoke 通过也不能证明长期任务质量。因此，发布评估应由离线测试、在线 Smoke/金丝雀、人工评审和生产监控组成连续闭环，各自提供不同类型的证据。

**摘要：**以离线回归作为候选版本准入，以部署后 Smoke/小流量金丝雀验证真实环境，以人工评审处理高风险和模糊案例，并以生产监控和反馈闭环持续兜底。任何关键失败都应按组织预先批准的风险规则阻断放量；具体数值阈值需结合业务基线校准。

本报告依据本轮成功抓取或搜索核验的官方产品文档与可观测性文档提出评估框架。来源没有给出适用于所有企业 Agent 的统一数值门槛；文中阻断条件、零容忍规则和监控就绪判定均为建议性治理设计，不是来源标准，需按业务风险、历史基线和可接受损失校准。

## 关键发现

1. **四类机制互补，不能互相替代。** 离线测试适合可重复的版本比较和回归；在线 Smoke/金丝雀验证部署环境与有限真实流量；人工评审处理语义模糊、复杂轨迹和高风险例外；生产监控持续发现运行偏差并支持定位与处置。
2. **Agent 离线评估应检查过程而不只是答案。** 可将任务结果、工具选择、参数、关键中间步骤和轨迹纳入评估；结合确定性代码检查、人工校准、LLM-as-judge 或成对比较。数据集、参考答案和评估器本身都需要治理。[LangSmith Evaluation concepts](https://docs.langchain.com/langsmith/evaluation-concepts)
3. **Smoke 的价值在于部署后、放量前验证关键路径。** 金丝雀可分阶段扩大流量并结合阶段分析或验证任务；但通用部署文档没有规定 Agent 专属用例、质量阈值或回滚判据，团队必须自行定义。[Google Cloud Cloud Deploy canary](https://docs.cloud.google.com/deploy/docs/deployment-strategies/canary)；[AWS Operational readiness](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/operational-readiness.html)
4. **人工评审应成为明确的风险控制点。** 对高影响、低置信度、策略冲突、异常工具行为及自动评估分歧设置升级、暂停或审批路径，并记录理由和处置；评审发现应转化为回归用例。
5. **生产监控提供运行证据，但遥测不等于质量证明。** traces、metrics、logs 可帮助关联任务、模型/工具调用和故障链路；仍需业务质量信号、人工升级和事件闭环。[OpenTelemetry Observability primer](https://opentelemetry.io/docs/concepts/observability-primer/)

## 证据与分析

### 四类评估的职责边界

| 机制 | 时点与目标 | 主要覆盖与证据 | 主要盲区/失效模式 |
|---|---|---|---|
| 离线测试 | 开发及候选版本发布前；比较版本、发现回归 | 版本化数据集、参考输出/元数据、运行结果、评分和执行轨迹；检查最终结果及工具调用等中间行为 | 数据集不代表真实任务或边界情形；评分标准/评估器偏差；离线通过不保证线上环境表现 |
| 在线 Smoke / 金丝雀 | 部署后、小流量及逐步放量阶段；验证服务就绪和关键端到端路径 | 关键依赖、代表性任务/工具链、错误与延迟等运行信号、阶段验证结果 | 用例过窄、观察时间或流量不足；未定义失败阻断、暂停和回滚动作；通用平台不提供 Agent 质量标准 |
| 人工评审 | 基准校准、上线前风险审查、线上异常升级 | 代表性/争议样例、执行轨迹、评审理由、审批与处置记录 | 评审标准不一致、抽样偏差、覆盖不足；若不沉淀为回归测试则难以持续改进 |
| 生产监控 | 全量运行期间持续进行；发现异常、定位原因、支持处置 | traces、metrics、logs，以及按任务/版本/工具链关联的反馈和事件记录 | 埋点缺失、告警噪声或漏报；遥测不能单独证明任务正确；隐私、访问、保留和成本风险 |

离线评估的实验数据结构和评估方法可支持版本间比较。OpenAI Evals 官方指南本轮抓取内容被截断，仅能确认 Evals 工作流及 Graders 文档入口；该页面不作为具体 Agent 评估方法或发布门槛的证据。[OpenAI Evals（有限核验）](https://developers.openai.com/api/docs/guides/evals)

在线发布方面，Google Cloud 文档支持渐进式流量发布、阶段分析及 verify/predeploy/postdeploy 等编排位置；AWS Well-Architected 强调运行就绪审查、检查清单和 runbook/playbook。两者提供的是通用部署与运行治理机制，不是 Agent 专属评估规范。生产可观测性方面，OpenTelemetry 文档支持以 traces、metrics、logs 理解系统状态，但人工监督和风险审批流程仍需组织自行设计。

### 建议的分层发布门槛

以下所有阻断条件、零容忍规则和监控就绪判定均为本报告提出的**建议性治理设计**，不是上述来源规定的行业统一标准。所有数值阈值（如错误率、延迟、观察时长、流量比例、抽样比例和非劣界限）应由团队基于风险等级、历史波动和业务目标设定。

**第 0 层：离线准入**
- 候选版本应有版本化、可复现的数据集，明确任务/组件指标、评分规则和已批准基线。
- 覆盖最终任务结果及关键中间行为（如工具选择、参数、轨迹）；确定性约束优先用代码评估器，主观质量由人工校准的评估器或成对比较辅助。
- 建议阻断条件：关键安全/策略用例出现已确认的严重违规，或关键指标出现未解释的严重回归。其他指标按预先批准的非劣界限判断；具体界限需本地校准。

**第 1 层：部署后 Smoke 与小流量金丝雀**
- 在真实部署环境验证服务就绪、关键依赖、代表性端到端任务和工具调用链；每个放量阶段检查服务错误、延迟及 Agent 任务/工具行为信号。
- 建议阻断条件：关键 Smoke 失败、关键依赖不可用或出现严重安全事件时停止推进；其余信号须处于预先批准的服务目标/基线范围。
- 放量前明确暂停/回滚责任人、操作步骤和验证任务。阶段分析能力本身不等于自动具备正确的 Agent 回滚判据。

**第 2 层：人工风险审查与例外审批**
- 对高影响、低置信度、策略冲突、异常工具行为及离线/线上评估分歧案例设置人工升级；记录样例、轨迹、理由、决定和处置。
- 建议阻断条件：高风险案例未完成审查，不扩大到更高风险或更大用户范围；评审发现的问题应转成回归用例或运行控制。

**第 3 层：生产监控就绪与反馈闭环**
- 持续关联 traces、metrics、logs 与版本、任务、工具链；建立告警责任人、人工接管、事件复盘和回归修复流程，并治理敏感遥测数据。
- 建议就绪条件：关键遥测可用、告警有明确责任人且处置可执行；若关键遥测缺失、告警无人负责或无法执行处置，不应视为监控就绪。达到团队定义的严重事件条件时暂停放量或回退。
- 将线上反馈和人工评审结果转为离线回归样例，形成“发现—分级—处置—修复—复测”的闭环。

### 适用场景与取舍

低风险、稳定且可自动判定的任务，可更多依赖离线回归和确定性 Smoke，并以人工抽样校准、生产监控兜底。工具链复杂或环境依赖强的 Agent，应提高部署后端到端 Smoke 和金丝雀的重要性，同时确保工具失败、重试和人工接管可观测。高影响或安全敏感任务，应采用更严格的离线风险用例、人工审批/升级和小流量发布。任务分布变化快时，应强化线上反馈回流；不能仅凭短时 Smoke 通过推断长期质量稳定。

## 建议

1. **建立统一评估清单和版本化证据包**：每次发布保存候选版本、数据集版本、评估器/提示版本、离线结果、Smoke 结果、人工例外审批、监控与回滚方案。
2. **把门槛写成可执行的发布状态机**：每层明确通过、阻断、人工例外、暂停和回滚条件；禁止以“总体分数不错”覆盖关键安全失败或关键依赖故障。
3. **按风险分级设阈值，而非套用单一行业数字**：先用历史基线和业务损失定义非劣界限、观察窗口、抽样比例及告警阈值；在数据不足时采用更保守的人工复核和受控放量。
4. **让人工评审与自动化形成闭环**：评审标准先校准，记录理由；将确认的问题加入离线回归集，并验证修复版本是否消除问题。
5. **把监控就绪纳入发布准入**：确保关键任务链路可追踪、告警有责任人、处置/回滚可执行，同时落实遥测数据最小化、访问控制和保留策略。
