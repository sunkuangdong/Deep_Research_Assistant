# Reliable Asynchronous Image-Generation Workflows: Architecture Report

## Background

Image generation is a long-running external operation with multiple independently failing boundaries: the client-facing API, durable work dispatch, a model provider, object storage, and a relational database. A robust design should not treat a successful HTTP response, provider completion, object publication, and database completion as one atomic event. The evidence reviewed supports explicit asynchronous acceptance and status monitoring, at-least-once queue handling, and conditional object publication. Provider-specific execution guarantees and relational transaction patterns were not established by the retrieved source content, so recommendations in those areas are identified as architectural guidance rather than documented guarantees.

## Key Findings

1. **Make the job resource the durable API contract.** HTTP `202 Accepted` means processing has been accepted but is not complete, and does not guarantee that the request will ultimately be acted upon. RFC 9110 says the response ought to describe current status and point to or embed a status monitor. Return a stable job identifier/resource and explicit state rather than implying the image is ready. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)
2. **Assume queue redelivery and duplicate work.** Amazon SQS visibility timeout temporarily hides a received message; it is not an exclusive lock. Standard queues provide at-least-once delivery and can deliver duplicates. Workers must be duplicate-safe and should acknowledge/delete only after durable completion or recording. [Amazon SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)
3. **Separate provider execution from result publication.** The official OpenAI image-generation guide was retrieved, but its substantive content was truncated in this run. Provider response formats, background execution, output retrieval, and retry/duplicate-generation semantics therefore remain unverified. Do not claim exactly-once generation or assume a timed-out provider call is safe to repeat. [OpenAI image-generation guide](https://developers.openai.com/api/docs/guides/image-generation)
4. **Use conditional object writes to prevent silent overwrites.** Amazon S3 documents `If-None-Match: *` create-only writes, with `412 Precondition Failed` when the key already exists; concurrent delete/write cases can produce `409 Conflict` with operation-specific retry behavior. These controls protect publication, not provider execution or database state. [Amazon S3 conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)
5. **Coordinate database state and dispatch with durable handoff and reconciliation.** The collected findings do not verify PostgreSQL transaction guarantees or a transactional-outbox source. As an architectural recommendation, persist the job and idempotency association before acknowledging acceptance, use an outbox or equivalent durable handoff, and reconcile database state with queue and object publication after partial failures. The AWS idempotency page was fetched but returned only a generic/truncated shell, so detailed idempotency guidance is not independently verified from it. [AWS Builders’ Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

## Evidence and Analysis

### Recommended lifecycle

A practical workflow separates durable acceptance, execution, and publication:

1. **Accept:** Validate the request and caller scope. In one database transaction, create a job record and persist the caller’s idempotency key association. Record a state such as `queued` and an immutable request fingerprint. Return `202 Accepted` with the job resource URI and current state only after the durable record and dispatch intent are committed.
2. **Dispatch:** Publish work through a transactional outbox or equivalent durable handoff. This is a design recommendation; the sources collected here do not establish a particular relational database/outbox guarantee. A dispatcher retries unsent outbox entries, while consumers tolerate duplicate messages.
3. **Execute:** A worker claims the job using a conditional/versioned state transition or lease, records an attempt, and invokes the model provider. Treat provider timeouts and lost responses as ambiguous outcomes. Keep provider attempts distinct from the logical job and avoid blind retries where duplicate generation or cost may result.
4. **Publish:** Store the generated bytes under a stable job/result identity. Where overwrite prevention is required, use S3 create-only conditional writes. Interpret `412` as a collision requiring reconciliation, not automatically as a generation failure; handle `409` according to the documented operation-specific behavior.
5. **Finalize:** Persist the result object reference and terminal job state. If object publication succeeds but the database update fails, reconciliation should detect the existing object and complete the state transition without regenerating unnecessarily. If the database says success but the object is absent or inaccessible, mark the job for repair or failure handling rather than returning a broken result.
6. **Observe:** Expose a durable status resource with terminal result/error details. Webhooks may complement polling, but the job resource should remain authoritative because webhook delivery guarantees were not established by the evidence collected.

### Comparison and trade-offs

| Boundary | Evidence-supported behavior | Architectural implication and trade-off |
|---|---|---|
| API acceptance | `202` is acceptance, not completion; a status monitor is the recommended response pattern. | A job resource adds API/state-management work but gives clients a stable recovery path and avoids holding requests open for model latency. |
| Queue | SQS visibility is temporary suppression; at-least-once delivery and duplicates are possible. | Duplicate-safe workers and durable completion-before-acknowledgement are necessary. Visibility extension can help long jobs but does not create exclusive execution. A DLQ helps isolate persistent failures but requires replay/reconciliation policy. |
| Provider | The retrieved OpenAI guide did not expose substantive behavior in this run. | Provider retries, output recovery, and duplicate-generation risk must be verified for the chosen provider. Model invocation should be treated as an uncertain external side effect, not an exactly-once transaction. |
| Object storage | S3 conditional writes can prevent overwrites and document 409/412 outcomes. | Stable keys and conditional creation reduce accidental replacement. Storage retry rules must remain separate from model-generation retry policy. |
| Relational database | No database transaction/outbox evidence was retrieved. | A database-led job state plus durable dispatch intent and reconciliation is a recommended pattern, not a guarantee established by these sources. It adds operational machinery but addresses split-brain outcomes across database, queue, provider, and storage. |

### Failure handling priorities

- **Lost API response after acceptance:** client retries with the same idempotency key; returning the existing logical job rather than creating another is a recommended contract, not a guarantee verified from the AWS idempotency page. Define behavior for reuse with different request parameters.
- **Worker crash or duplicate delivery:** allow redelivery, use conditional state transitions/leases, and acknowledge only after durable progress is recorded. Do not interpret queue visibility as a lock.
- **Provider timeout:** record an ambiguous attempt and apply provider-specific recovery rules. The evidence does not establish whether a retry duplicates generation or whether a prior result can be retrieved.
- **Storage collision:** use conditional writes and reconcile the existing object with the job record. Do not overwrite blindly or rerun generation solely because publication returned a conflict.
- **Database/object divergence:** run reconciliation for stale nonterminal jobs, orphaned objects, and terminal records with missing outputs. This is an architectural recommendation; no database-specific guarantee was verified.

## Recommendations

1. **Use an asynchronous job API:** return `202`, a stable job ID/resource URI, and explicit initial state; provide polling and optionally webhooks. Keep the job resource authoritative.
2. **Persist before acknowledging:** commit the job record and idempotency association before returning acceptance. Use a transactional outbox or equivalent durable dispatch mechanism to avoid a committed job with no queued work. These are recommended design choices; the collected sources do not verify a specific database implementation or guarantee.
3. **Design for at-least-once execution:** make queue consumers idempotent at the logical-job level, use conditional/versioned state transitions, and acknowledge messages only after durable progress. Configure visibility extension and a DLQ based on workload and recovery policy.
4. **Treat provider calls as ambiguous external side effects:** record attempts and provider request identifiers where available; verify the selected provider’s timeout, retry, background-job, and output-retrieval semantics before enabling automatic retries.
5. **Publish outputs safely:** use stable result identities and S3 conditional creation when overwrites are unacceptable. Handle `409` and `412` according to the operation and reconcile before retrying generation.
6. **Build reconciliation and observability from the start:** track job state, attempt count, queue age, provider latency/errors, storage publication outcomes, and time spent in nonterminal states. Provide repair paths for stuck jobs and orphaned objects. These are operational recommendations, not sourced performance claims.
7. **Define retention and access controls:** keep generated objects private by default, issue authorized access paths, and define cleanup/retention for failed outputs and incomplete multipart uploads. The collected evidence specifically supports lifecycle cleanup for incomplete multipart uploads; broader security/retention details require separate validation.

## Limitations

- The OpenAI image-generation page was retrieved, but its substantive content was truncated; provider request/response formats, background execution, output encoding/retrieval, and retry semantics were not verified.
- The AWS Builders’ Library idempotency page was fetched as a generic/truncated shell. Its detailed guidance could not be independently verified from this run.
- No relational database documentation was preserved in the findings. Transactional outbox, isolation, leases, and reconciliation are architectural recommendations, not sourced database guarantees here.
- No webhook-specific delivery guarantees were retrieved; signing, ordering, retries, and acknowledgement behavior remain unspecified.
- S3 evidence is specific to conditional writes; broader consistency behavior was not independently verified.
- No workload, latency, cost, or failure-rate data was collected, so the report makes no quantitative performance claims.

**Conclusion:** The most defensible architecture is a durable asynchronous job resource backed by duplicate-tolerant workers, explicit provider-attempt tracking, conditional result publication, and database/queue/storage reconciliation. The first three mechanisms are supported to varying degrees by the cited HTTP, SQS, and S3 documentation; database coordination and provider retry policy remain implementation recommendations requiring validation against the chosen database and model provider.
