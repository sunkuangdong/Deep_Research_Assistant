# LLM 服务故障弹性设计：调研报告

## 背景

LLM 服务调用依赖外部提供商、网络和模型运行时，可能遇到速率限制、账户配额、连接或处理超时、服务端错误及区域/模型级故障。与普通无状态读取不同，生成请求可能消耗显著推理资源；客户端超时也不能证明提供商未完成请求。若无边界地重试，可能放大过载、延长用户等待、重复计费，或重复触发工具与外部副作用。

因此，弹性设计不应只是“失败后重试”，而应先识别故障性质，再在统一时限和成本预算内组合有限重试、熔断、备用路径、降级与幂等控制。以下结论综合 OpenAI、Anthropic、Google Cloud、AWS 与 Microsoft Azure 的官方文档及 Claude 状态页；供应商特定行为不应直接外推到其他 API。

## 关键发现

1. **先分类，避免把所有错误都当作瞬时故障。** Anthropic 的错误文档区分请求错误、认证/权限、账单、限流、内部错误、处理超时和暂时过载等类别；其 429 可能对应速率限制或支出上限。OpenAI 文档则说明速率限制与额度不足等错误情形；两家供应商的错误语义应分别处理，不能互相外推。请求格式、认证、权限、账单或持续配额问题通常应修复根因，而不是循环重试。[Anthropic API 错误文档](https://platform.claude.com/docs/en/api/errors)；[OpenAI API 错误码](https://developers.openai.com/api/docs/guides/error-codes)

2. **对可恢复故障采用有限、带上限且有抖动的退避。** Google Cloud 将 408、429、5xx 及部分连接中断列为通常可重试的瞬时问题，并强调操作幂等性；AWS 建议限制重试次数、设置退避上限并加入随机抖动，以减少同步重试造成的流量尖峰。若响应提供有效的 `Retry-After`，应将其纳入等待决策；本次证据未核实该头在所有 LLM API 中的保证或统一语义，不能假定所有 429 都提供该头或代表同一种故障。[Google Cloud 重试策略](https://docs.cloud.google.com/storage/docs/retry-strategy)；[AWS 超时、重试与抖动退避](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)

3. **重试与熔断职责不同。** 重试用于短暂、可能自行恢复的失败；熔断用于持续故障，通过快速失败或转备用路径，避免反复调用继续占用资源并造成级联影响。恢复时应有限开放探测，再逐步恢复流量。按提供商、模型或区域等故障域隔离熔断，是工程设计建议而非来源规定的统一实现；具体阈值、窗口和冷却时间需按业务验证。[Azure 断路器模式](https://learn.microsoft.com/zh-cn/azure/architecture/patterns/circuit-breaker)

4. **降级或切换不是无条件的“透明替代”。** 备用模型/提供商可能在上下文限制、工具调用、结构化输出、延迟、成本、拒答和安全策略上不同。应预先验证兼容性并定义可接受的降级，例如缩短上下文、改用较小模型或关闭非关键功能；不满足质量或安全要求时，应明确失败而非静默改变语义。供应商状态页可辅助判断，但不能替代本地按模型/区域/功能观测的错误率和延迟。[Claude Status](https://status.claude.com/)

5. **幂等性与统一 deadline 是重试和切换的安全边界。** 超时后上游可能仍在执行；重放可能重复推理、计费或工具副作用。应按端点核实供应商幂等键/去重能力，并在应用侧为工具执行建立请求关联、去重和状态检查。所有尝试、退避等待及备用路由应共享同一端到端 deadline；流式调用区分首 token 等待与整体生成时长属于工程建议，具体行为需按 API 验证。[Google Cloud 重试策略](https://docs.cloud.google.com/storage/docs/retry-strategy)；[AWS 超时、重试与抖动退避](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)

## 证据与分析

### 故障分类与动作映射

| 故障类别 | 典型处理 | 主要注意事项 |
|---|---|---|
| 请求、认证、权限、账单或确定性配额问题 | 停止自动重试，修复请求/配置/账户；仅在备用端权限与额度已验证时切换 | Anthropic 的 429 可能是速率限制或支出上限；OpenAI 错误语义应按其文档单独判断，不能只凭状态码推断 |
| 可恢复限流 | 遵循有效等待提示，有限退避并加入抖动；控制并发与总尝试 | 不假定每个 429 都有 `Retry-After`；区分速率限制与持续额度限制 |
| 连接失败、部分 5xx、暂时过载 | 在剩余预算内有限重试；持续失败时熔断并评估备用路径 | 多层重试会放大流量；避免 SDK、应用和网关同时重试 |
| 超时 | 先判断请求阶段、是否已有流式输出或副作用；在幂等/去重保障下决定重试 | 客户端超时不等于上游未执行；重放可能重复计费或执行 |
| 持续提供商/模型/区域故障 | 对相应故障域熔断，半开时限量探测；必要时切换或降级 | 状态页只是运营信号；备用能力与安全、成本、权限需预先验证 |

### 机制取舍与协同

退避重试提高短暂故障下的成功机会，但会增加延迟、费用和上游负载；熔断牺牲短期尝试机会，换取故障期间的资源保护和快速失败。两者应串联而非互相替代：先在有限预算内处理短暂故障，若失败持续或熔断已打开，则停止重试并快速失败或转入已验证的备用路径。备用路径仍共享原请求的 deadline 和成本约束。

幂等性决定重放是否安全，超时预算决定重试/切换是否仍有意义，故障分类决定应采取哪种动作。对流式生成，首 token 超时与生成中断应分别观测；已有输出或工具动作后，自动重放可能造成重复内容或副作用。是否支持续传、取消或安全重放取决于具体 API 与应用协议，不能假定跨供应商一致。

### 证据边界

官方资料支持通用重试、超时、抖动和断路器原则，也提供了特定供应商的错误分类与状态信息；但没有给出适用于所有 LLM 服务的统一重试次数、超时、熔断阈值或半开探测比例。Anthropic 的错误码和 SDK 行为是供应商特定定义；Google Cloud Storage 的重试原则可作设计参考，但其 SDK 默认值不能直接套用于 LLM API。关于跨提供商能力等价、流式重放和端点级幂等保证，现有证据不足，需按实际 API 与业务工作流验证。

## 建议

1. **建立错误分类表和统一处理入口。** 记录提供商、模型/区域、HTTP 状态码或流内错误、错误体、`Retry-After`（若有）、请求阶段及本地超时。将确定性请求/账户问题与瞬时限流、连接失败、5xx、过载和超时分开处理。
2. **只在一个主要层实施重试。** 设置最大尝试次数、带上限的指数退避与随机抖动；若响应提供有效服务端等待提示，将其纳入等待决策，但不要假定所有 429 都提供该提示或具有相同语义。避免 SDK、应用、代理和网关层层重试。
3. **为每个请求设统一端到端 deadline。** 单次连接/请求超时、退避等待和备用路由都从同一预算扣除；剩余时间不足时停止重试，返回可解释错误或按业务规则降级。流式请求分别监控首 token 与整体生成时长；这是需按具体 API 验证的工程建议。
4. **按故障域实施熔断和受控恢复。** 对提供商—模型—区域等维度观测失败率与延迟；持续故障时打开熔断，冷却后只放行少量半开探测，成功后逐步恢复。阈值、窗口、冷却时间和探测比例通过 SLO、流量测试与故障演练确定。
5. **把幂等性作为重试/切换门槛。** 核实具体端点的幂等键或去重语义；对工具调用和外部副作用实施应用侧去重、请求关联与状态检查。无法确认上游是否已执行时，不要无条件重放。
6. **预先验证备用模型与降级策略。** 建立能力矩阵，验证上下文、工具、结构化输出、安全策略、权限、区域、延迟和成本；明确哪些任务允许缩短上下文、切换较小模型或关闭非关键功能，哪些任务必须失败关闭。
7. **结合本地指标与供应商状态页。** 按模型、区域、功能监控错误率、延迟、超时、重试量、熔断状态、切换率和成本；状态页作为辅助信号，不作为单次请求健康保证。

## 局限性

- 本次证据未确定跨供应商通用的重试次数、超时、熔断阈值、冷却时间或半开探测比例；这些参数必须结合 SLO、流量、成本和故障演练设定。
- OpenAI 错误文档的抓取内容未能核实 `Retry-After` 的具体保证及端点级幂等语义；不能假定所有 429 都带该头，也不能假定重试一定安全。Anthropic 对 429 的支出上限语义是其供应商特定定义，不应外推到 OpenAI。
- Anthropic 错误码与 SDK 默认重试行为仅适用于其文档所述 API/SDK；Google Cloud Storage 的具体 SDK 默认值不应直接外推到 LLM 服务。
- 未对备用提供商的能力等价性、价格、权限、区域可用性或安全策略进行实测比较；切换与降级建议属于需应用级验证的工程策略。
- 状态页可能存在更新延迟且只覆盖所列组件/事件；流式续传、生成中断和工具执行语义依赖具体 API 与应用实现。
