# LLM 服务故障下的弹性设计：调研报告

## 背景

LLM 服务调用依赖外部提供商、网络和模型推理资源，限流、超时、连接异常及提供商不可用都可能造成请求失败或延迟。弹性设计的目标不是无限重试，而是在端到端时限和业务语义约束下，区分可恢复故障与永久性错误，控制请求放大，保护调用方资源，并在主路径不可用时提供安全、透明的替代行为。

## 关键发现

1. **故障分类是所有恢复动作的前提。** 限流、超时、网络/连接异常和提供商暂时不可用可作为暂时性故障候选；鉴权、参数格式等非暂时性错误通常不应通过重复请求解决。熔断统计也应聚焦依赖健康故障，避免把调用方错误误判为提供商故障。这是通用工程建议，具体错误语义须按目标提供商和端点核实。
2. **重试应有限、带抖动并受总时限约束。** OpenAI 官方限流指南支持指数退避与随机抖动，并提醒失败请求仍可能计入速率限制；Google Cloud Storage 文档将 408、429、5xx、socket timeout 和 TCP disconnect 列为该产品通常可重试的暂时性故障。Storage 的规则不能直接视为所有 LLM API 的承诺。[OpenAI 限流指南](https://developers.openai.com/api/docs/guides/rate-limits)；[Google Cloud Storage 重试策略](https://docs.cloud.google.com/storage/docs/retry-strategy)
3. **熔断用于持续故障止损，降级用于业务连续性。** Azure 通用架构文档描述了 Closed（关闭、正常放行）、Open（打开、快速拒绝）和 Half-Open（半开、有限探测）状态。降级可按业务语义选择备用模型/提供商、缓存、预设答复、有限功能或明确不可用提示。降级结果应标明来源和质量，不能伪装成正常模型输出；这些是通用架构建议，并非 LLM 专属规范。[Azure 熔断器模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker)
4. **超时不等于服务端未执行。** 通信失败或响应丢失后，重复提交可能重复计费、创建任务或触发工具副作用。RFC 9110 的幂等语义允许在通信失败后重试幂等请求，但不意味着任意 POST 都可安全重放；应用层幂等键或业务去重需由目标服务支持。[RFC 9110，第 9.2.2 节](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)；[Stripe 幂等请求文档](https://docs.stripe.com/api/idempotent_requests)
5. **机制应分层协作，而非互相替代。** 分类决定动作；退避重试处理短暂故障；幂等性约束重放安全；熔断隔离持续故障；降级决定用户侧替代路径。所有动作都应受端到端时限、重试预算和业务副作用约束。

## 证据与分析

### 故障分类与动作映射

下表是通用设计参考，不是所有 LLM 提供商的统一错误码规则。具体状态码、错误语义及可重试性必须按目标提供商和端点文档核实，并结合实测校准。

| 故障类别 | 建议处理 | 主要风险 |
|---|---|---|
| 限流（例如某些 API 返回 429） | 遵循提供商提示（若有），采用有上限的指数退避与随机抖动；控制总尝试次数和总等待时间 | 快速重试可能继续消耗配额并加剧限流 |
| 超时、连接中断 | 先判断请求是否可安全重放；在预算内有限重试；持续发生时纳入熔断健康信号 | 超时只表示调用方未及时收到结果，服务端可能已完成操作 |
| 暂时性服务端错误/提供商不可用 | 短暂波动可有限重试；持续故障由熔断快速隔离并进入降级 | 重试放大负载、资源被慢调用占用 |
| 鉴权、参数或请求格式错误 | 通常停止自动重试，返回可诊断错误并修正配置/请求 | 错误地重试会浪费预算，甚至污染熔断统计 |

Google Cloud Storage 文档列出的 408、429、5xx、socket timeout 和 TCP disconnect 是该产品文档中的重试参考，不应直接视为 LLM API 的统一规则。下述重试层级、熔断统计和降级标识属于基于通用架构原则形成的工程建议，而非特定提供商对 LLM 服务的承诺。

### 机制比较与取舍

- **退避重试**适合短暂、可能恢复且请求可安全重放的故障。指数增长、随机抖动、最大等待、最大尝试次数和总时限共同限制重试风暴；重试责任应集中在一个明确层级，避免 SDK 与应用层叠加。集中重试责任是通用工程建议。
- **熔断**适合持续性依赖故障，目标是快速失败、释放资源并避免级联影响。阈值过敏会误熔断，过迟则无法及时止损；Half-Open（半开）探测应受控，避免恢复中的提供商被瞬时流量压垮。
- **降级**适合业务允许替代结果或部分能力的场景。备用模型、缓存和预设答复在质量、新鲜度、安全性及成本上各有取舍；高准确性或强时效场景可能应明确返回暂不可用，而非提供未经验证的替代内容。
- **幂等与去重**是有副作用请求安全重放的基础。RFC 9110 定义幂等关注多次执行的预期效果，不保证响应完全相同；Stripe 文档展示了 API 幂等键机制，但不能据此推断特定 LLM 生成端点支持幂等键。

### 综合设计

建议按“请求预算与分类 → 重试/幂等控制 → 熔断与恢复 → 降级响应 → 观测校准”组织调用链。短暂限流或网络波动在预算内退避；持续超时或提供商不可用触发熔断；可能产生副作用的请求在重放前必须具备服务端幂等支持或业务级去重。超时、重试、熔断和降级均应纳入端到端时限，避免恢复策略本身拖垮用户请求。

## 建议

1. **建立错误分类表。** 按提供商和端点记录状态码、错误类型、传输异常及是否可重试；将调用方错误与依赖健康故障分开统计。具体映射以目标提供商最新文档和实测为准。
2. **设置统一的请求预算。** 为端到端请求、单次调用、重试等待和降级预留时间；采用有限次数/总时限的指数退避与随机抖动。若服务端提供明确等待提示，可优先遵循，但不得突破总预算。
3. **明确重试责任层。** 选择 SDK 或应用编排层中的一个主要重试控制点，审查其他层的默认重试，防止重试次数乘积式增长。这是通用工程建议，需结合所用 SDK 的实际行为验证。
4. **对副作用操作实施幂等保护。** 同一逻辑操作在重试时保持稳定的幂等键，或使用业务级去重；先确认目标 LLM API、任务服务及工具端点确实支持该语义。无法保证安全时，不要仅因超时盲目重放。
5. **按提供商/依赖边界配置熔断。** 以时间窗口内的相关失败触发 Open（打开），恢复后仅放行有限 Half-Open（半开）探测；按故障类型区分阈值，并提供状态监控和必要的人工恢复控制。阈值和窗口需由实际服务目标校准。
6. **设计透明的降级路径。** 预先定义备用模型、缓存、预设答复、有限功能和明确不可用提示的适用条件；向调用方标识降级状态、来源或质量，避免误导用户。
7. **持续观测与演练。** 监控故障类别、超时、重试次数与耗时、熔断状态、探测结果、降级比例及重复请求/幂等冲突；通过故障注入或演练验证恢复路径，并依据真实时延分布和业务 SLO 校准参数。

## 局限性

本次证据包含五个不同页面：OpenAI 官方限流指南、Google Cloud Storage 重试策略、Azure 通用熔断器模式、Stripe 幂等请求文档和 IETF RFC 9110。熔断与降级依据是通用架构模式，并非 LLM 专属规范；Google Cloud 重试规则来自 Storage 产品文档，不能直接推广为所有 LLM API 的服务端行为。现有材料未能确认特定提供商的超时重试规则、Retry-After 行为、生成端点幂等键支持、错误码映射或备用模型能力。未提供实际流量、时延分布、SLO、成本和业务副作用清单，因此不对超时值、重试次数、熔断阈值或缓存有效期给出固定数值；实施前需针对目标 API 与业务流程验证。
