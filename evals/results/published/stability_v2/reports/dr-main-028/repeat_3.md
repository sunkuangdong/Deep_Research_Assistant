## 背景

RAG 检索评估不是单一问题：系统可能漏掉相关材料、把有用材料排得太靠后，或虽检索到相关内容却没有覆盖回答所需的全部事实。Recall@K、MRR、nDCG 与证据覆盖率分别观察这些不同环节，不能互相替代，也不能单独证明最终生成答案正确。

本报告区分“检索结果相关性/排序”与“回答所需证据是否齐全”。其中 nDCG 的排序折扣与理想排序归一化可由 scikit-learn 官方 API 文档直接核验；RAGAS 官方文档说明 Context Recall 的 claim 支持判断及 Context Precision 的排序相关性定义。Recall@K、MRR 的公式和适用场景按通行信息检索定义整理，但本轮未检索到可直接核验其公式的官方原始页面。

## 关键发现

- **Recall@K 看覆盖候选，不看前 K 内的次序。** 它衡量已知相关文档/片段中有多少进入前 K 个结果，适合检查生成器可见范围内是否找全材料。K 应与实际送入生成器的候选数或上下文预算一致。
- **MRR 看首个相关结果出现得多早。** 它适合通常只需一个可用结果的 FAQ、导航或单答案检索；若答案需要多条证据共同支撑，MRR 会忽略首个相关项之后的证据。
- **nDCG@K 看前 K 的整体排序质量，并可利用分级相关性。** 高相关结果排得越靠前，得分通常越高。它适合多文档/多证据检索，但必须明确相关性等级、增益函数、K 和未标注项处理方式。
- **证据覆盖率看回答所需事实是否能从检索上下文中找到。** RAGAS Context Recall 的 LLM 版本将参考答案拆成 claims，判断每条 claim 是否受上下文支持；它与 Recall@K 的参照对象不同：前者以答案 claims/参考信息为参照，后者以已知相关文档或片段集合为参照。
- **标注成本取决于参照数据和粒度。** 二元相关性判断通常比 nDCG 所需的分级相关性标签粗；Context Recall 可用可信 reference 作为参考上下文的代理，减少逐条标注 reference_contexts 的工作，但仍需参考答案、LLM 评估及抽样复核。现有来源没有提供可比较的人工工时或费用数据。

## 证据与分析

### 指标含义与适用场景

| 指标 | 核心问题 | 主要标注需求 | 适用场景与边界 |
|---|---|---|---|
| Recall@K | 已知相关材料有多少进入前 K？ | 查询—文档或查询—chunk 的相关集合；通常可用二元相关性，但相关集合应尽量完整 | 适合候选召回与漏检诊断；不区分前 K 内的排序，也不证明证据足以回答问题 |
| MRR | 首个相关结果排在第几位？ | 判断结果是否相关，并确定首个相关项排名 | 适合只需一个可用结果的任务；忽略后续相关项和相关程度差异 |
| nDCG@K | 按相关等级加权后，前 K 排序整体如何？ | 文档/chunk 的分级相关性或可作为增益的真实分数 | 适合多证据、排序位置重要的任务；不同增益函数、K 和标注处理会影响可比性 |
| 证据覆盖率（如 RAGAS Context Recall） | 回答所需事实有多少能由检索上下文支持？ | 可信参考答案/claims，或参考上下文、文档 ID 等参照数据；LLM 版本还需评估与复核 | 适合多事实问题的证据完整性检查；不直接衡量检索列表排序，也不等于生成答案忠实或正确 |

Recall@K 与证据覆盖率都涉及“是否找齐”，但分母和判断单位不同，不能直接互换。MRR 与 nDCG 都对位置敏感，但前者只看首个相关项，后者汇总前 K 并可体现相关等级。scikit-learn 的 nDCG 文档说明其实现按预测分数诱导排序，对真实分数应用对数折扣并除以理想 DCG；跨实现比较时应统一口径。

RAGAS 的 Context Precision 可作为边界参照：它关注相关 chunk 是否排在不相关 chunk 前面，属于排序质量；Context Recall 则关注参考答案 claims 是否被上下文支持。两者互补。RAGAS 文档说明 reference 可作为 reference_contexts 的代理，降低逐条建立参考上下文的工作量，但这并不消除参考答案质量、LLM 判断偏差和人工抽查成本。

### RAG 场景下的解释限制

传统排序指标通常把靠前位置赋予更高权重。2025 年 arXiv 预印本提出，这种用户逐条浏览的假设未必完全符合 LLM 整体处理检索上下文的方式，并指出“相关但无助或会干扰生成”的内容可能需要单独考虑。该观点是研究者提出的评估局限，不是普遍定论；摘要页也不足以独立核验其报告的实验细节。因此，传统指标适合作为检索诊断信号，但不应被当作端到端生成效用的完整代理。

### 标注成本判断

成本只能作定性比较，不能据现有来源给出工时或费用排名。二元相关性标注通常比多级相关性标注要求更粗；Recall@K 还依赖较完整的相关项集合，标注池不完整可能使召回率偏高。nDCG 需要定义等级并对候选结果作分级判断。证据覆盖率若逐条标注参考上下文，前期成本可能较高；以 reference 作为代理可减少这部分工作，但仍需可信参考答案，并承担 LLM-as-judge 的推理成本和抽样人工复核。实际成本还取决于查询复杂度、chunk 粒度、标注指南、评估规模和复核比例。

## 建议

1. **按诊断问题选指标，不追求单一总分。** 漏检看 Recall@K；首个可用结果的速度看 MRR；多条结果的整体排序与相关等级看 nDCG@K；回答所需事实是否齐全看 Context Recall。
2. **RAG 检索评估采用互补组合。** 可用 Recall@K 检查生成器可见范围内的候选覆盖，用 nDCG@K 检查排序质量；多事实问题再加入证据覆盖率。若产品体验依赖首个证据快速出现，可额外报告 MRR。
3. **评估粒度贴近实际流水线。** 若生成器消费 chunk，就在 chunk 粒度评估；若先检索文档再切片，应分别记录文档召回与最终上下文覆盖，避免粒度错配。
4. **预先固定评估协议。** 明确 K、相关性等级、nDCG 增益函数、参考答案/参考上下文定义、未标注项处理和候选池构造；对标注池完整性及 LLM 判断做抽样复核。
5. **把检索评估与端到端评估分开报告。** 检索指标不能单独证明答案完整、忠实或正确；应另行评估生成答案质量，并关注无助或干扰证据。

综合而言，Recall@K、MRR、nDCG 与证据覆盖率分别回答候选覆盖、首项位置、整体排序和答案所需证据完整性问题；建议按任务组合使用，并将其作为检索诊断而非端到端答案质量的替代指标。

## 局限性

- 本轮未检索到可直接核验 Recall@K 与 MRR 公式的官方原始页面；NIST TREC 页面仅支持评测背景，不是具体指标规范。Stanford IR Book、NIST reciprocal-rank 指标文档、BEIR 页面及 RAGChecker 官方页面未取得可引用目标页面，因此未据此补充定义或作工具间比较。
- nDCG 的增益函数、截断 K、未标注项处理会影响结果；Recall@K 等依赖相关项集合的指标也受标注池完整性影响。
- RAGAS 文档支持指标定义和输入方式，但没有提供人工标注工时、费用或不同方案的量化对比；成本判断为定性推论。LLM 判断质量、语言适配、模型费用和人工复核比例会因数据集与实现而异。
- arXiv 来源为预印本摘要页面，关于传统位置折扣与 LLM 消费方式不匹配的观点应视为研究假设/研究结论，而非普遍定律。
- 本报告未计算任何数据集上的指标值，也未对指标作数值排名。
