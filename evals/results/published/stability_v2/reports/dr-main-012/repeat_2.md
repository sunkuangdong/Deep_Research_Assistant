# 企业 RAG 系统中的提示注入风险与防御方案

## 背景

检索增强生成（RAG）把外部文档、知识库内容与用户请求一并提供给模型。提示注入的核心风险在于模型可能无法稳定地区分“指令”与“数据”。在本报告采用的工作定义中，直接提示注入指用户输入中包含试图改变模型行为的指令；间接提示注入则指类似指令藏在模型处理的外部内容中，例如被摄取或检索的文档、邮件和网页。现有可核验证据对直接注入的定义性覆盖较弱，因此此处作为风险分析的操作性区分，而非声称已由多来源充分确证的分类。间接注入使知识库来源、摄取流程和检索结果都成为信任边界的一部分。

风险严重程度取决于系统权限。仅生成文本时，主要后果可能是回答被操纵或敏感信息被输出；若 RAG/agent 还可访问邮件、文件、浏览器或业务 API，恶意内容可能诱导模型发起数据外传或其他有害操作。因而防护不能只依赖提示词或单一检测器，而应在数据、内容、工具和输出链路设置可由应用服务端强制执行的控制。

## 关键发现

1. **间接注入扩大了攻击入口。**攻击者可将恶意指令嵌入外部内容，使其随检索结果进入模型上下文。Anthropic 的代理案例展示了邮件中的隐藏指令诱导代理将机密邮件转发到外部地址；InjecAgent 学术基准研究了工具集成代理中的数据窃取和有害操作意图。该基准报告的结果仅适用于其特定评测配置，不能直接视为企业 RAG 的普遍攻击成功率。
2. **工具能力会把内容风险转化为操作风险。**模型若能调用具有宽泛权限的工具，注入可能从错误回答升级为敏感数据外泄或未经授权的副作用。模型生成的工具调用不能充当授权凭证。
3. **数据隔离与工具授权是硬边界，过滤与提示处理是纵深防御。**检索前按身份限制可见数据，工具网关按身份、资源、参数和动作授权；内容过滤和“不可信内容”标记可降低风险，但不能替代权限检查，也不能保证识别所有注入。
4. **输出验证必须覆盖下游消费路径。**结构/schema 校验、敏感信息检查、引用与证据一致性检查，以及对代码、SQL、URL、HTML 和工具参数的安全处理，可阻止不可信输出直接进入执行或渲染环节；验证失败应拒绝、重试或转人工。
5. **控制应组合并持续验证。**多租户、高敏知识库优先验证文档级授权和缓存边界；连接外部工具的系统应强化工具最小权限、动作分级和高影响操作确认；开放摄取场景需加强来源治理、内容筛查和回归测试。

## 证据与分析

### 风险机制与影响

直接注入与间接注入的区分在此作为操作性威胁模型：前者从用户输入进入，后者从外部内容进入。两者都涉及模型对指令与数据边界处理不可靠这一共同机制；间接注入额外依赖内容来源、摄取和检索链路。Anthropic 的邮件代理示例说明隐藏指令可能导致机密邮件外发；InjecAgent 研究覆盖工具集成代理中的数据窃取和有害操作。后者的实验结果是特定基准结果，不应外推为企业 RAG 的总体风险率。

### 控制边界与取舍

| 控制 | 主要作用 | 不能替代/典型失效点 |
|---|---|---|
| 数据隔离 | 在检索前按已认证用户/组限制索引或文档可见范围，降低越权检索和跨租户暴露。Azure AI Search 文档说明了服务角色、数据平面角色及索引范围等配置边界。 | 服务级 RBAC 不等于文档级授权；身份映射、缓存或过滤位置错误仍可能造成越权。它不判断文档是否含恶意指令。 |
| 内容过滤 | 对用户输入、摄取内容和检索片段进行风险筛查，监控异常输入/输出。 | 过滤器可能漏检新颖或隐蔽指令，也可能误报；不能作为唯一安全边界或授权机制。 |
| 不可信内容处理 | 保留检索片段来源与信任标签，将文档作为数据/引用而非系统指令，并限制模型可见上下文。 | 仅靠提示词要求模型忽略文档指令并不可靠；标签在摘要、拼接或转换中丢失也会削弱效果。 |
| 工具授权 | 由服务端工具网关校验调用者身份、资源范围、参数和动作类型；工具凭据最小化，读写/导出/删除分权，高影响操作可要求人工确认。 | 只校验工具名称、权限过宽、把模型调用当授权或确认流程可绕过，都会留下风险。它不保证模型请求本身正确。 |
| 输出验证 | 在模型与下游系统之间校验 schema、敏感信息、策略和证据一致性；对可执行/可渲染内容做编码、沙箱化或拒绝执行。 | 仅格式校验不足；验证后再拼接、遗漏执行路径或失败仍放行，可能绕过控制。它不能撤销已发生的越权检索或工具副作用。 |

### 综合判断

这些控制分别约束“能取到什么”“内容是否可疑”“外部文本是否被当作指令”“能执行什么”以及“输出能否被下游消费”，彼此互补而不可互换。默认实施顺序应先建立身份与数据边界，并为有副作用的工具设置服务端授权；随后统一处理不可信内容、增加过滤与监控，并对所有下游消费实施输出验证。该顺序是基于风险链条的定性工程建议，不是来源实测的效果排名。

证据方面，Microsoft Learn 提供 Azure AI Search RBAC 与索引范围的产品级说明；Google SAIF 提供安全框架层面的原则；OWASP 项目总览提供 LLM 应用风险类别背景；Anthropic 与 InjecAgent 支持代理场景中的攻击机制和影响案例。将这些原则映射到企业 RAG 的具体实现，部分属于工程推导，需结合实际身份源、租户模型、数据分类和工具清单验证。工具网关、人工确认、输出 schema/语义验证、沙箱化等具体措施是基于风险链条的架构建议，并非上述来源对某一企业 RAG 实现效果的直接实测证明。

## 建议

1. **检索前执行授权。**以已认证身份和组成员关系过滤检索范围；分别验证服务级、索引级和文档级权限。避免先取回越权内容再要求模型忽略；检查跨租户索引、缓存和身份映射边界。优先采用细粒度身份/RBAC，限制服务凭据范围，并避免向终端用户暴露管理密钥。
2. **把外部内容默认视为不可信。**对用户输入与检索片段分别检查；保留来源、租户和信任标签；在上下文构造中明确区分系统指令与引用数据，限制模型只接收完成任务所需的片段。不要把提示词分隔或“忽略文档指令”当作安全边界。
3. **在摄取、检索和生成环节部署内容筛查。**按风险检查恶意指令特征、敏感信息和不允许内容；记录过滤决策并监控异常。过滤器应作为纵深防御，配合来源治理、人工处置和持续回归测试，而非承诺完全阻断提示注入。
4. **通过工具网关实施最小权限。**每次调用由服务端校验用户身份、资源范围、参数和动作；工具使用独立、最小权限凭据；读与写、查询与导出、低风险与高影响操作分级。对外发邮件、删除、批量导出、状态变更等动作设置确认或审批，并记录审计事件。此处为架构层面的工程建议，需按具体工具和业务风险验证。
5. **验证所有模型输出及下游参数。**对结构化输出执行 schema 校验；检查引用是否支持结论、是否包含敏感信息或违反策略；对 SQL、代码、URL、HTML 和工具参数进行上下文编码、白名单校验、沙箱化或拒绝执行。验证失败时安全拒绝、重试或转人工，禁止失败后默认放行。具体验证器和策略需针对下游系统测试，不能假定单一校验器可消除语义风险。
6. **建立可审计的持续验证闭环。**记录调用身份、检索文档标识与范围、过滤结果、工具调用和输出验证结果；日志避免不必要地保存敏感正文。用红队和回归测试覆盖恶意文档、跨租户检索、越权工具调用、输出注入及控制绕过，并在模型、索引、提示模板或工具权限变更后重新验证。
7. **按部署场景调整重点。**纯文本问答重点关注数据隔离、内容处理、敏感信息和证据一致性；多租户/高敏知识库优先验证文档级授权与缓存隔离；连接邮件、文件、浏览器或业务 API 的系统，应把工具授权与数据隔离作为关键硬边界，并覆盖所有执行入口。

## 局限性

本次可核验证据主要包括浏览器代理案例、工具集成代理基准、云平台产品文档和安全框架原则，并非对企业 RAG 部署的全面实测。将代理场景的攻击链映射到 RAG，依据的是外部内容进入模型上下文这一共同机制；具体风险仍取决于知识库来源、检索授权、模型能力和工具权限。InjecAgent 的实验结果不能作为企业系统的普遍成功率。

本轮未检索到 OWASP LLM01/LLM06 专项页面正文，也未检索到 NIST 对抗性机器学习分类的可核验原始页面；因此未将这些页面的具体条目作为结论依据。Google SAIF 与 OWASP 项目总览支持框架/风险类别层面的论据，但部分 RAG 控制建议属于工程化映射。缺少企业自身的身份与租户模型、数据分类、工具清单、攻击测试结果和控制失效率，无法量化风险降低幅度或成本收益；建议需在目标架构中通过威胁建模和测试验证。
