# Deployment Strategy for a FastAPI and React AI Application

## Background

A production deployment for a FastAPI API and React frontend must coordinate independently deployable application artifacts with shared operational concerns: database schema evolution, traffic admission, observability, and recovery. AI workloads can include long-running requests and external model/provider dependencies, so health checks should distinguish process health from the ability to serve traffic. Rollback must also account for the fact that reverting application code does not necessarily reverse database changes.

The evidence reviewed includes official Docker, FastAPI, Alembic, Kubernetes, and PostgreSQL documentation. It supports a practical deployment pattern, but does not prescribe a complete reference architecture for this exact stack.

## Key Findings

1. **Build reproducible, lean container images.** Docker multi-stage builds allow build-time tools and intermediate artifacts to be excluded from the final image. A practical layout is a Node stage that builds React assets and a separate Python build/runtime path for FastAPI; serve the static frontend and API in separate containers or services unless there is a deliberate reason to combine them. FastAPI's official example packages the API and dependencies in a Linux container and runs the server as the foreground process. These are applications of the official guidance, not a mandated combined-stack recipe. ([Docker multi-stage builds](https://docs.docker.com/build/building/multi-stage/); [FastAPI in Containers](https://fastapi.tiangolo.com/deployment/docker/))

2. **Run schema changes as a controlled release step.** Keep database changes in versioned Alembic migration scripts, review the operations and generated SQL, and define downgrade behavior where it is genuinely safe. Prefer an expand-and-contract sequence for changes that must coexist with old and new application versions: add compatible schema first, deploy code that can work with both forms, backfill if needed, then remove obsolete schema only after rollback to the old code is no longer required. A downgrade is not a substitute for restoring deleted or transformed data. Alembic documents migration operations and upgrade/downgrade functions, but the exact orchestration and compatibility policy must be designed for the application. ([Alembic Operation Reference](https://alembic.sqlalchemy.org/en/latest/ops.html))

3. **Use health checks for distinct decisions.** Kubernetes separates startup, readiness, and liveness probes. Use startup checks to allow legitimate initialization time, readiness to decide whether an instance should receive traffic, and liveness to detect a process that should be restarted. Avoid making liveness depend on transient external services or database availability if that would create restart loops. For an AI API, readiness can reflect whether the service can safely accept work; dependency checks should be bounded and designed so a provider outage does not cause every API process to restart. ([Kubernetes probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/))

4. **Emit structured operational logs to the platform.** Use consistent machine-readable fields such as timestamp, severity, service/version, request or trace ID, route, latency, and migration/release identifier. Send logs through the container runtime's standard output/error collection path and centralize retention and access controls. Do not log credentials, prompts, personal data, or model responses by default; apply redaction and sampling where needed. This is a recommended operational pattern, not a verified claim from the Twelve-Factor logging page, which was not retrieved in this run.

5. **Make rollback code-safe and schema-aware.** Deploy immutable, versioned images and retain the previous known-good frontend and API artifacts. Use rolling or blue/green/canary rollout with readiness gates, then shift traffic only after smoke tests. If application behavior regresses, route traffic back to the prior image. Keep database changes backward-compatible across the rollback window; use a forward fix or restore from a tested backup for irreversible data changes rather than assuming a migration downgrade can recover data. For PostgreSQL indexes where write availability matters, `CREATE INDEX CONCURRENTLY` can avoid blocking concurrent writes, but it has caveats and should be monitored and failure cleanup planned. ([PostgreSQL CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html))

## Recommendations

The following are implementation recommendations synthesized from the cited platform documentation and general operational practice; the sources do not prescribe a complete deployment pipeline for this exact stack.

- **Separate build and runtime concerns:** build React assets in a named Node stage; build and run FastAPI in a minimal Python runtime image. Pin dependencies and base images, scan images, run as a non-root user, and inject secrets at runtime rather than baking them into images. These security controls are prudent but are not established by the Docker/FastAPI pages cited here. Keep frontend and API independently versioned where that simplifies rollout and rollback.
- **Use a release pipeline with explicit gates:** build and test immutable images; run unit/integration tests; apply backward-compatible migrations once as a controlled job; deploy the API and frontend; wait for startup/readiness; run smoke tests; then progressively shift traffic. Avoid having every API replica race to run migrations at startup. These orchestration details are recommended design choices, not requirements stated by the cited sources.
- **Adopt expand-and-contract migrations:** first add compatible structures, deploy code that tolerates old and new schema, backfill in bounded batches, switch reads/writes, and remove old structures in a later release after the rollback window. Take and verify backups before destructive changes. Treat data restoration as a separate recovery procedure. The reviewed Alembic reference documents migration operations but does not itself prescribe this rollout pattern or guarantee downgrade safety.
- **Define probe semantics explicitly:** startup probe for initialization, readiness for traffic eligibility, and liveness for unrecoverable process failure. Keep probe endpoints lightweight and bounded; do not make liveness a broad dependency health test. For AI workloads, use request timeouts, concurrency limits, and queueing/backpressure separately from health probes. Kubernetes documents the probe distinctions; the AI-specific controls are application-level recommendations.
- **Standardize structured logs and correlation:** emit JSON logs with request/trace IDs and release identifiers; centralize collection, retention, and alerting; redact secrets and sensitive user/model content. Pair logs with metrics and traces for latency, error rate, saturation, migration status, and provider failures. These are operational recommendations, not claims verified against the Twelve-Factor logging page, which was not retrieved.
- **Prepare rollback before release:** retain prior image digests and deployment manifests; define rollback triggers (for example, sustained error/latency regression or failed smoke checks); test traffic reversal and database recovery in staging. Roll back application artifacts first when schema compatibility permits; use forward-only repair or backup restore for irreversible schema/data changes. This is a recommended safety pattern; the reviewed sources do not validate a particular rollback mechanism or guarantee data recovery.

## Limitations

The official sources establish container build mechanics, a basic FastAPI container pattern, Alembic migration operations, Kubernetes probe distinctions, and PostgreSQL concurrent-index behavior. They do not establish a single best deployment platform or a complete production architecture for React + FastAPI + AI. The Twelve-Factor logging page was not retrieved, so logging recommendations here are operational guidance rather than a source-verified summary of that page. The PostgreSQL source output was truncated before all caveats, and the Alembic material reviewed does not guarantee that downgrades are safe for application data. Exact rollout strategy, backup/restore objectives, AI provider dependency policy, and compliance controls depend on the chosen infrastructure and workload.

This run used `--no-analysis`; no analyst stage was performed.
