## 背景

企业 AI Agent 的一次执行可能跨越多次模型调用、工具调用、队列投递和人工审批，并可能长时间等待外部响应或审批。作为架构判断，平台不应把“当前运行进程”当作任务本身：进程可能重启，消息可能重复投递，外部工具可能已产生副作用但响应丢失，审批也可能尚未返回。可靠设计的核心是把执行状态持久化、把异步交接做成可恢复、把重复执行纳入常态，并明确每个故障边界的责任。

本报告依据本轮检索到的 Temporal、LangGraph、AWS SQS、AWS 事务发件箱及 Google Cloud Tasks 官方页面。Cloud Tasks 页面正文在本轮抓取中不足以核实其投递与重试语义，因此不据此作产品能力判断。

## 关键发现

1. **执行状态与长期业务记忆应分开存储。** LangGraph 文档区分 thread 级 checkpointer 与跨 thread 的 store；内存检查点在进程重启后丢失，生产环境应使用持久化后端，并管理检查点增长与保留。Temporal 官方文档将其定位为故障后可恢复执行的平台，但本轮所见首页未展开具体机制或保证边界。
2. **队列至少一次投递意味着消费者必须容忍重复。** AWS SQS 标准队列可能重复投递；事务发件箱可把业务数据与待发布事件放在同一数据库事务中，降低数据库与消息发布的双写不一致，但转发器仍可能重复发送。
3. **幂等性必须覆盖业务副作用，而不只是消息去重。** 为业务事件设置稳定标识，在消费者侧将去重登记与业务状态更新置于同一原子边界；对外部工具调用，优先传递幂等键。若外部系统不支持幂等，则需可恢复状态机、补偿或对账机制。队列的去重能力不能证明跨系统端到端“恰好一次”。
4. **人工审批应是持久化工作流中的显式等待状态。** 保存任务/线程标识、待审批内容、审批状态和恢复所需上下文；审批身份授权、重复提交、超时、撤回及恢复协议需由平台应用层明确实现。现有 LangGraph 持久化概览未验证具体审批 API 或安全保证。
5. **故障恢复应按层定义重试、确认和隔离。** 分别处理数据库事务、发件箱转发、队列投递、消费者执行、外部工具副作用和审批等待；设置有限重试、退避、死信/隔离与告警，避免无限重试和毒消息阻塞。具体参数需按业务验证，现有来源未给出通用值。

## 证据与分析

### 推荐的逻辑架构

- **任务/工作流状态库**：建议保存任务 ID、租户、当前阶段、版本、检查点、待执行动作、审批等待状态、重试元数据及最终结果。可评估版本号或乐观并发控制，以避免并发 worker 覆盖新状态。此处的字段与并发控制属于架构建议；来源支持持久化检查点和恢复需求，但未规定统一 schema。
- **长期业务数据存储**：保存跨任务共享的用户偏好、知识或业务实体，与执行检查点分离，按租户授权、保留期和数据治理要求管理。LangGraph 文档明确区分 thread 级检查点与跨 thread store。
- **任务队列与调度器**：队列只承载可重建的任务引用/命令及必要元数据，不把队列当作唯一事实来源。任务状态先持久化，再通过事务发件箱发布待执行事件，避免数据库提交与消息发布的双写窗口。消费者领取任务后校验状态版本与租约/可见性，完成后再确认；租约细节需按所选队列实现验证。
- **幂等账本与工具适配层**：建议以稳定的业务操作 ID（例如任务 ID + 步骤 ID + 操作版本）作为幂等键，记录请求摘要、执行状态、外部返回值和完成时间。重复请求返回已记录结果或进入核对流程；不要仅以队列消息 ID 作为跨重试、跨重新排队的业务幂等键。该键构造是建议，不是来源规定。
- **审批服务**：将审批建模为 `WAITING_APPROVAL` 等持久状态，记录审批对象版本、审批人/角色、决策、时间戳和审计事件。审批通过后可采用条件更新/唯一决策约束推进状态，并发布恢复事件；拒绝、超时、撤回和重复提交均应有明确终态或转移规则。具体安全控制需结合企业身份系统设计。
- **恢复与运维面**：建议提供超时扫描/租约回收、有限重试与退避、死信隔离、人工重放、检查点清理、审计日志、队列积压和恢复时长监控。重放前检查幂等账本及外部副作用状态，避免把“重新执行”误当作“从未执行”。

### 关键取舍与适用场景

| 维度 | 设计取舍 | 适用判断 |
|---|---|---|
| 检查点 vs. 长期存储 | 检查点优化恢复；长期存储服务跨任务共享。混用会造成状态膨胀、生命周期和权限边界不清。 | 长任务、审批等待需要持久化执行状态；跨会话记忆另设存储。 |
| 事务发件箱 vs. 直接发布 | 发件箱降低数据库与队列双写不一致，但增加转发器、清理和重复投递处理。 | 数据库变更必须可靠触发异步任务/事件时优先评估。 |
| 至少一次 vs. 去重 | 至少一次更能容忍故障，但要求消费者幂等；去重窗口不等于外部副作用恰好一次。 | 默认按可能重复设计；对不可逆工具调用尤其需要幂等键或补偿。 |
| 自动重试 vs. 隔离 | 重试可恢复暂时性故障；无限重试会放大故障并阻塞资源。 | 暂时性错误有限重试；永久错误进入隔离/死信并告警。 |
| 工作流引擎 vs. 自建状态机 | 工作流引擎可提供长任务执行抽象；自建可贴合业务但需自行承担恢复、重放和运维复杂度。 | 依据团队运维能力、任务时长、审计要求和现有平台评估；本轮证据不足以对产品作性能排名。 |

### 典型故障与恢复路径

1. **worker 在工具调用前崩溃**：租约到期后重新领取；从持久化状态恢复到该步骤，按幂等键执行。
2. **工具已成功但响应丢失**：不能盲目重复不可逆操作。先用同一幂等键查询/重试外部接口，或进入对账/人工核验；记录“结果未知”状态。
3. **数据库提交成功但消息未发布**：事务发件箱在同一事务中保存业务变更和待发事件，转发器恢复后继续投递。
4. **消息已投递但发件箱未标记完成**：允许重复投递，由消费者幂等账本吸收重复；不要假设发件箱提供端到端恰好一次。
5. **审批等待期间进程重启**：从持久化等待状态恢复，不依赖原进程内存；审批回调需校验任务版本、授权和重复决策。
6. **毒消息或永久错误**：有限重试后隔离，保留错误上下文与审计信息，支持受控修复和重放。

### 证据边界

AWS 官方资料明确支持 SQS 标准队列至少一次投递及消费者幂等要求，并说明事务发件箱用于缓解双写不一致、仍可能重复发送。LangGraph 官方持久化页面支持检查点与跨线程 store 的区分、内存检查点重启丢失及检查点保留成本。Temporal 页面支持其可恢复执行定位，但本轮未核实具体重放语义、持久化实现或保证边界。Google Cloud Tasks 官方入口虽成功抓取，但正文不足，不能据此断言其投递次数、重试参数或执行保证。

本轮没有可比的吞吐量、延迟、成本、故障率或恢复时间数据，因此不提供数值排名或性能结论。架构建议是基于上述事实的设计推导，不应视为产品对端到端保证的承诺。

## 建议

1. **以持久化状态机/工作流作为任务事实来源**：每个任务有稳定 ID、明确状态转移、版本和审计记录；执行检查点与跨任务记忆分层存储。
2. **把审批等待纳入工作流状态**：审批请求可恢复、可审计、可授权；对重复提交、超时、撤回、拒绝和审批后恢复定义确定性规则。
3. **默认采用至少一次思维设计消费者**：任务可重复投递；消费者以稳定业务幂等键保护数据库变更和工具副作用，并保存可查询的执行结果。
4. **在数据库与队列之间使用事务发件箱（适用时）**：转发器可重试，消费者必须幂等；对顺序敏感事件维护明确序列。
5. **为外部工具调用建立“结果未知”处理**：优先使用外部幂等键/查询接口；不支持时采用补偿、对账或人工核验，避免自动重试造成重复扣款、重复发送等不可逆后果。
6. **定义分层故障策略并演练**：为每层设定超时、有限重试、退避、隔离、告警和人工重放流程；演练 worker 重启、消息重复、发送后崩溃、审批等待恢复、外部响应丢失及检查点清理。
7. **先验证产品语义再做选型承诺**：对候选工作流引擎/队列逐项验证持久化范围、恢复/重放语义、重复投递、顺序、保留策略、审批集成和灾备恢复；本轮材料不足以对 Temporal、LangGraph 或 Cloud Tasks 作统一性能/可靠性排名。

## 局限性

- Temporal 来源为官方文档首页，本轮未核实具体持久化机制、重放语义、人工审批 API 或保证边界。
- LangGraph 来源为 Persistence 概览，未核实专门的人工审批 API、安全授权、审批超时及完整恢复协议。
- AWS 来源未给出通用幂等键格式、去重记录保留期限、统一重试次数/退避参数或跨外部系统副作用的通用实现。
- Google Cloud Tasks 页面正文证据不足；其投递语义、重试配置和可靠性边界未确认，不能从 SQS 类推。
- 本轮未展开状态库/队列自身不可用、备份恢复、跨区域灾备及恢复目标（RTO/RPO）；这些应作为后续设计与演练范围。
- 缺少可比的性能、成本、可用性和恢复时间数据；报告提供的是架构原则与验证清单，而非量化选型结论。
