# Agent 工具路由方案对比：规则、传统分类模型与 LLM

## 背景
Agent 工具路由负责把用户请求映射到可用工具，并决定是否调用、调用哪个工具以及传递哪些参数。基于规则的方案通过显式条件触发动作；传统分类模型从标注样例学习固定类别，再将预测类别映射到工具；LLM 路由则根据自然语言上下文和工具定义生成工具选择及参数。三者的差异不仅是模型能力，也涉及控制边界、运行链路、维护方式和失败风险。

本次核验的官方文档说明，OpenAI、Anthropic 与 Gemini 均提供模型发起工具调用、由应用或服务执行工具的机制；Anthropic 文档还展示客户端工具调用的请求—执行—结果回传流程。Rasa 文档描述按意图组织 NLU 训练样例，scikit-learn 文档提供分类评估指标；AWS 文档展示规则条件评估与重定向行为。上述文档没有提供三类路由在统一任务、硬件和负载下的准确率、延迟或成本对照，因此以下性能比较以机制分析和工程建议为主，不作无依据的量化排名。

## 关键发现
1. **没有证据支持普遍的准确率赢家。** 规则对明确、稳定、可枚举的条件可直接表达；分类模型依赖代表性标注样例；LLM 可处理上下文丰富的自然语言请求，但工具 schema 只约束输出形状，不能保证工具选择或参数语义正确。应在统一标注集上比较，而不是跨产品文档推断优劣。
2. **延迟与成本取决于端到端实现。** 简单规则可能避免模型推理；分类器成本受模型、特征处理和部署影响；LLM 工具调用可能增加模型往返、工具执行和结果回传。没有同条件基准，不能断言某类方案必然更快或更便宜。
3. **可解释性与审计能力不同。** 显式规则通常更容易追踪命中条件；分类器可记录预测类别、特征和模型版本，但决策未必直观；LLM 的结构化调用记录能审计工具名、参数和结果，却不等于完整解释模型为何选择该工具。
4. **失败处理必须由应用层设计。** 规则需要默认/未知分支和冲突检测；分类器需要低置信度拒识、人工复核或安全回退；LLM 需要 schema 与业务校验、缺参澄清、权限检查、超时/异常处理及副作用控制。
5. **分层混合通常比单一机制更稳健。** 可用规则执行权限和硬约束，用分类器处理稳定常见类别，让 LLM 处理开放、上下文复杂的请求，并统一设置拒识、校验、人工确认和安全回退。这是工程建议，不是来源文档保证的性能结论。

## 证据与分析

### 五维对比

| 维度 | 基于规则 | 传统分类模型 | LLM 路由 |
|---|---|---|---|
| 工具选择准确率 | 对明确条件可精确编码；覆盖不足、条件重叠或优先级错误会导致漏路由/误路由。 | 可从样例学习表达变化；效果依赖标注质量、类别边界和训练验证流程。 | 可利用上下文选择工具并生成参数；schema 不保证语义正确，仍需业务校验。当前没有三者统一基准。 |
| 延迟 | 简单匹配可能较低开销；复杂规则链、外部查询也会增加耗时。 | 取决于模型规模、特征处理、运行时和服务架构。 | 可能包含模型调用、工具执行、结果回传及后续生成；并行可减少独立任务串行等待，但增加并发管理。 |
| 成本 | 需计入规则开发、维护、执行资源和外部依赖。 | 需计入标注、训练、部署、推理和维护。 | 需计入模型调用、上下文、工具执行和结果处理。没有可比的统一成本数据。 |
| 可解释性 | 条件—动作映射通常便于审查；规则规模增长后冲突和维护复杂度上升。 | 可记录预测、特征和版本，但模型决策未必直观。 | 可审计调用工具、参数和结果，但调用轨迹不等于模型选择理由的完整解释。 |
| 失败处理 | 默认分支、冲突检测、无匹配告警和回归测试。 | 置信度阈值、拒识、人工复核、漂移监控和安全回退。 | schema/业务校验、缺参澄清、权限检查、超时与异常处理、幂等和高风险确认。 |

### 准确率评估方法
应使用同一标注集、同一工具集合和同一业务判定标准，至少报告总体表现、类别级 precision/recall、误路由代价、覆盖率与拒识率。precision/recall、误路由代价、覆盖率和拒识率是对单一总体 accuracy 的补充评估维度，并非本次调研得到的实测结果。还应单独测试未见表达、缺参、多意图请求和高风险工具调用。类别不平衡时，单一 accuracy 可能掩盖关键工具类别的失败；因此应结合混淆矩阵及与业务风险相匹配的指标。

### 延迟与成本评估方法
在目标部署环境测量端到端 p50/p95/p99 延迟、吞吐、资源占用和单位任务成本，统一纳入预处理、路由决策、模型/服务调用、工具执行、重试、结果回传和后处理。记录负载、工具数量、上下文规模、并发策略与缓存条件；将单次推理成本与标注、规则维护、监控和故障处置等生命周期成本分开。当前来源没有同条件实测数据，不能据此给出快慢或成本排名。

### 适用场景与取舍
- **规则优先**：条件稳定、边界清楚、工具集合有限，或需要强约束和明确审计路径。主要代价是规则覆盖、优先级和回归维护。
- **传统分类模型优先**：输入表达多样但路由类别相对固定，且有代表性标注数据和训练/验证/发布流程。主要代价是数据维护、漂移监控和低置信度处理。
- **LLM 路由优先**：请求开放、上下文依赖强，且需要从自然语言组织工具参数；前提是系统能承担模型调用、校验和失败兜底。主要代价是调用链复杂、延迟/成本需实测，且结构化输出不保证语义正确。

### 综合判断
三类方案不存在由当前证据支持的普遍优胜者。规则强调显式控制，分类模型适合固定类别的样例学习，LLM 适合开放式上下文理解与参数生成。生产系统可采用分层路由：规则先处理权限、禁用工具和确定性强的路径；分类器处理稳定常见类别；LLM 处理开放复杂请求；应用层统一执行 schema、业务和权限校验，并对低置信度、异常和高风险副作用设置拒识、人工确认或安全回退。该组合是基于机制的工程推断，需通过目标业务的离线评估和线上监控验证。

## 建议
1. 先定义工具类别、误路由代价、拒识条件和高风险操作边界，再选择路由器；不要先以模型新颖度决定方案。
2. 建立统一标注评测集，按类别报告 precision/recall、误路由代价、覆盖率和拒识率，并纳入缺参、未见表达、多意图及权限边界测试。
3. 在目标环境对端到端延迟和成本做同条件基准测试，分别核算推理与生命周期成本；不以理论推断替代实测。
4. 采用分层混合架构：规则负责硬约束，分类器负责稳定常见类别，LLM 负责开放复杂请求；所有路径都经过应用层校验和审计。
5. 为每类路由设置明确失败策略：规则默认分支与冲突告警、分类器低置信度拒识、LLM 缺参澄清与工具异常处理；高风险副作用要求授权/确认、幂等和重试上限。

## 局限性
本次官方来源主要描述 API、训练数据格式、分类评估指标和具体规则产品行为，没有提供三类方案在统一数据集、硬件、负载和工具链下的准确率、延迟、吞吐或成本基准。可解释性、维护成本和混合架构收益属于工程推断，需结合具体业务验证。OpenAI 页面抓取内容有限，Gemini 页面核验范围也有限；Rasa 与 AWS 文档是具体产品文档，不能泛化为所有实现的保证。未检索到可用于量化比较的官方原始基准数据。
