# 生产环境向量数据库选型：成本与规模边界

## 背景

中小团队选择向量数据库时，不能只比较软件是否开源或套餐起价，还要同时考虑可承载的工作负载、扩展方式、基础设施账单、运维人力和可用性要求。Milvus Lite、Standalone、Distributed 分别对应嵌入式本地、单机服务器和 Kubernetes 分布式部署；托管服务则把部分底层运维交由供应商承担，但仍按资源或用量计费。

本报告以 Milvus 官方部署与架构文档，以及 Zilliz Cloud、Pinecone 官方定价页面为依据。官方给出的“几百万”或“约 1 亿”向量规模属于选型描述，不是对所有数据和负载的硬性容量上限或性能保证。

## 关键发现

1. **Lite 适合原型、边缘和单机嵌入，不宜把本地文件持久化等同于生产级服务保障。** 官方将 Lite 定位于小数据集，建议规模为最多几百万向量；它以 Python 库形式运行并将数据持久化到本地文件。官方功能对照还列出 Python 客户端、高级数据管理和消息队列等差异。若需要多客户端、访问控制、分区或服务端高可用，应评估其他部署形态。[Milvus 部署选项概述](https://milvus.io/docs/install-overview.md)

2. **Standalone 是小规模/早期生产的单机折中。** 官方称其适合不希望使用 Kubernetes、但有生产工作负载的场景；资源充足时可扩展至约 1 亿向量。该数字不是性能承诺，实际边界取决于单机资源、向量维度、索引、并发和延迟目标。单机形态意味着容量受单台服务器能力约束。[Milvus 部署选项概述](https://milvus.io/docs/install-overview.md)

3. **Distributed 提供按工作节点扩缩的能力，但成本和运维面显著增加。** Milvus 架构包含 Proxy、协调器、工作节点、元数据、对象存储和 WAL/消息系统；官方支持扩缩 Query、Data、Index、Proxy 等节点，但不支持增加 Coordinator。对象存储可能产生请求费用，整体成本还可能包括 Kubernetes、计算、元数据、WAL、网络、监控和冗余资源。[Milvus Architecture Overview](https://milvus.io/docs/architecture_overview.md)；[Scale a Milvus Cluster](https://milvus.io/docs/scaleout.md)

4. **托管服务的价格更可见，但不能仅凭起价判断总成本或容量。** Zilliz Cloud 页面列出免费方案、Serverless 起价及 Dedicated 方案，并按计算单元、集群类型、存储和工作负载参数估算；页面也提示估算可能与实际费用不同。Pinecone 的套餐包含最低月费及存储、读写单位、出口等计费项，价格随云和区域变化。[Zilliz Cloud Pricing](https://zilliz.com/pricing)；[Pinecone Pricing](https://www.pinecone.io/pricing/)

5. **现有证据不足以计算自建与托管的绝对成本盈亏平衡点。** 自建方案缺少统一的实例规格、节点数、冗余、云单价和运维人力数据；托管方案也缺少同一工作负载下的完整账单参数。公开套餐起点不能直接当作同等容量、性能或 SLA 的横向报价。

## 证据与分析

### 成本与规模比较

| 方案 | 成本构成与运维 | 规模边界与扩展 | 更适合的场景 |
|---|---|---|---|
| **Milvus Lite** | 无独立集群部署，但消耗宿主机资源；备份、恢复、资源隔离等生产保障需另行设计。 | 官方建议最多几百万向量；这是选型建议而非硬上限。材料未证明其具备服务器部署所需的 HA 或并发服务承诺。 | 原型、边缘设备、单机应用内嵌。 |
| **Milvus Standalone** | 单个 Docker 镜像运行于单机服务器；相较分布式部署，基础设施和组件管理面较少，但仍需管理单机、备份和恢复。 | 官方描述可用于早期生产，资源足够时约 1 亿向量；受单机能力约束，超过单机能力时应重新评估。 | 小规模早期生产、团队希望避免 Kubernetes，且可接受单机边界。 |
| **Milvus Distributed** | 计算资源之外，还需考虑 Kubernetes、元数据、WAL/消息系统、对象存储及请求、网络、监控和冗余；需要相应平台运维能力。 | 可按工作节点水平扩缩；Coordinator 不支持增加。官方材料未给出通用容量阈值或每节点容量。 | 需要按组件扩展、具备 Kubernetes/分布式系统运维能力的团队。 |
| **托管向量数据库** | 供应商承担部分底层基础设施管理；账单可能按存储、读写、计算、出口、区域及附加服务变化。 | 本次定价材料未提供可与 Milvus 部署形态对齐的统一容量或性能边界；需核验服务等级和合同。 | 希望快速上线、降低底层运维负担，且愿意按实际用量付费的团队。 |

### 公开价格的可比性

公开价格应按计价口径分组理解，而非做统一月费排名。Pinecone 页面列出 Builder $20/月、Standard 最低额 $50/月、Enterprise 最低额 $500/月；Zilliz Cloud 页面列出免费方案 $0/月、Enterprise Dedicated $197/月起，以及 Dedicated $126/GB/月起。后者按 GB 标示，与套餐最低月费不是同一口径，不能直接并列比较。Zilliz 页面另列每百万向量/月起始示例：分层存储型 $5、容量优化型 $16、性能优化型 $63。

这些数字仅说明各页面公开的价格结构和起始示例，不构成同等工作负载下的价格排名；云区域、读写负载、数据类型、集群配置和包含额度均会影响实际费用。自建方案没有足够的资源与单价输入，无法计算绝对月成本或盈亏平衡点。Lite/Standalone 的多项规模与功能结论主要依据同一份 Milvus 部署选项概述，来源页面数量满足要求，但不代表这些结论已由多个独立页面交叉验证。

### 规模边界与风险解释

“最多几百万”和“约 1 亿”是官方选型建议/描述，不是硬性容量上限或性能保证。Distributed 的官方资料说明了可扩缩节点类型，但没有给出通用向量容量阈值；托管定价页也没有提供可直接比较的容量边界。实际规模取决于向量维度、数据类型、索引、查询与写入比例、并发、延迟目标、硬件和配置，必须用目标工作负载压测验证。

高可用也不能从“持久化”或“分布式”字样直接推出：Lite 的本地文件持久化不构成 HA 证据；Standalone 的现有材料未承诺故障切换；Distributed 的架构/扩缩容页面未提供具体 SLA；托管定价页面未覆盖 SLA。生产评估应单独核验备份恢复、故障域、可用性承诺和恢复目标。

## 建议

- **验证阶段或边缘单机应用：优先考虑 Lite。** 适用于小数据集、Python 应用内嵌和快速验证；若生产需求涉及多客户端、访问控制、分区、服务端并发或 HA，不应仅凭本地文件持久化作出生产保障判断。
- **小规模早期生产：评估 Standalone。** 当团队希望避免 Kubernetes、单机资源足够且业务可接受单机边界时，它是较简单的生产起点。应以真实数据和查询负载验证内存、磁盘、延迟、备份恢复及故障恢复，并预先定义何时迁移。
- **需要横向扩展且有平台能力：评估 Distributed。** 适合需要按工作节点扩缩、并能承担 Kubernetes、存储/消息依赖、监控和容量规划的团队。预算应纳入所有依赖与冗余，而不只计算 Milvus 计算节点；扩缩容和版本兼容性需在目标版本验证。是否采用自建分布式部署，还应先核验团队实际运维能力、业务可用性要求和故障恢复责任，不能仅因需要横向扩展就默认 Distributed 是合适选择。
- **团队运维能力有限或希望快速上线：评估托管服务。** 先用免费额度或小规模试用，以真实读写比例、存储、区域和数据出口估算账单，再观察实际费用；同时核验 SLA、备份恢复、数据驻留、限额和迁移成本。不要把公开起价当作生产总成本。Zilliz Cloud 的页面展示计算单元/集群类型及向量参数等估算维度；Pinecone 页面列出存储、读写单位和出口等计费项，两者应分别按实际工作负载核算，不能把计费模型视为相同。
- **建立迁移触发条件，而非按向量数单点决策。** 结合资源利用率、P95/P99 延迟、吞吐、故障恢复目标、运维工时和月账单设定阈值；Lite 到 Standalone 有官方迁移路径，但 API 兼容不代表功能和性能完全相同。

## 局限性

本次官方资料未提供四类方案在同一工作负载下的完整价格、性能基准、硬性容量上限或可比 SLA，因此无法给出绝对成本排名、盈亏平衡点或确定的向量数切换线。托管价格会随云、区域、套餐和用量变化，页面估算不等于实际账单。Distributed 架构资料标示 v3.0.x，而扩缩容页面含较早版本示例，具体组件、命令和能力需按目标版本复核。建议在采购或上线前以目标数据、索引、并发和延迟目标进行压测，并核验服务商当前报价与合同条款。
