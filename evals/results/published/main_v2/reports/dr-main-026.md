# 企业 AI Agent 上线前评估体系与发布门槛

## 背景

企业 AI Agent 的行为不止是生成最终文本，还可能涉及规划、工具调用、状态变化、外部系统交互和多步执行。因此，单看最终答案或单一离线分数，无法充分判断 Agent 在目标环境中是否可靠。上线评估需要把可重复的离线测试、部署后的在线 Smoke、人工评审和持续生产监控组合起来，各自回答不同问题。

本报告依据本轮核验的五个不同规范化官方页面（来自 OpenAI、Google Cloud、LangChain 和 Microsoft 四个机构），提出一套分层发布门槛。文档支持评估数据集、Agent 工作流评估、追踪与标注等能力；具体门槛逻辑属于治理建议，不是这些平台文档规定的统一标准。来源数量按不同页面计数，LangSmith 的 Evaluation 与 Observability 是同一机构的两个页面，不作为两个独立机构来源。

## 关键发现

1. **离线测试用于可重复地比较版本、发现回归，但结论受测试集和判分规则约束。** LangSmith 文档描述了在整理的数据集上运行应用、比较版本、基准测试和发现回归，并可将历史轨迹或失败案例纳入数据集。[LangSmith Evaluation](https://docs.langchain.com/langsmith/evaluation) OpenAI 与 Google Cloud 的官方页面也提供 Agent 工作流/Agent 评估流程的相关依据。[OpenAI Agent evals](https://developers.openai.com/api/docs/guides/agent-evals)；[Google Cloud agent evaluation](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/evaluation-agents)

2. **Agent 评估应同时检查结果与执行过程。** 任务是否完成不能替代对工具选择、参数、调用结果、关键状态变化和终止条件的检查。最终答案正确可能掩盖不可靠或不安全的执行路径；反之，严格要求轨迹逐字一致也可能误罚等价的安全路径。过程指标和结果指标应并列解释，而非压成一个总分。此处具体检查项属于实施建议，需按 Agent 的工具和业务流程定义。

3. **在线 Smoke 是部署链路健康检查，不是质量或安全验收。** 建议在目标环境执行最小端到端请求，确认 Agent 能完成运行、取得响应、执行关键工具步骤并产生追踪数据。[Microsoft Learn：Trace and Observe AI Agents](https://learn.microsoft.com/en-us/azure/foundry-classic/how-to/develop/trace-agents-sdk) 该定义是根据官方端到端示例和追踪能力形成的操作建议，并非来源规定的正式 Smoke 标准。发布团队应在测试前记录预期结果、关键步骤和通过/失败判据。

4. **人工评审补足语义和业务判断，但必须有抽样与标注治理。** LangSmith 文档描述了通过 annotation queues 或 inline annotation 收集标注和反馈，并将追踪用于问题定位和后续评估数据集建设。[LangSmith Observability](https://docs.langchain.com/langsmith/observability) 单条反馈不代表总体质量；评审规范、抽样策略、严重性分级和升级流程需要组织自行定义，并保留评审记录。

5. **生产监控提供真实运行证据和故障定位线索，但可观测性不等于正确性保证。** Trace/span 可记录调用、状态、时间和层级等执行信息；内容记录可能受隐私策略限制，脱敏或关闭记录也会减少语义诊断上下文。监控必须与告警责任人、人工接管、降级和回滚机制配套。

## 证据与分析

### 四类评估机制的分工

| 机制 | 核心问题 | 主要证据 | 主要盲区 |
|---|---|---|---|
| 离线测试 | 已知案例上是否满足要求、相对基线是否回归？ | 固定数据集上的任务结果、工具调用与轨迹判分、版本对比 | 未覆盖的任务/环境/攻击不会自动显现；判分器和数据集代表性有限 |
| 在线 Smoke | 目标部署环境中的关键端到端链路是否可运行？ | 代表性请求的运行结果、关键步骤和追踪是否成功 | 少量请求不能代表真实流量；链路成功不证明答案正确或安全 |
| 人工评审 | 输出和执行是否在语义、业务及风险上可接受？ | 按规范抽样的人工标注、问题分级和处置结论 | 覆盖量受人力限制；抽样偏差和评审不一致会影响结论 |
| 生产监控 | 真实运行中发生了什么，是否出现异常或变化？ | Trace/span、性能与质量信号、用户反馈和告警 | 只观察已采集信号；追踪本身不证明正确性，隐私脱敏可能造成盲区 |

四类机制互补而不可互相替代：离线测试适合发布前回归；Smoke 适合部署后快速验证；人工评审适合高风险、语义敏感或自动判分不可靠的场景；生产监控适合持续发现真实流量中的异常。线上失败轨迹和人工反馈应回流为离线回归案例，形成“测试—发布—观察—复盘—再测试”的闭环。此闭环属于治理建议。

### 建议的分层发布门槛

以下是建议的治理门槛，不是来源规定的统一数值标准。现有证据没有给出通用成功率、样本量、抽样比例或告警阈值，因此不设定虚构数字。组织应在每次发布前将适用的测试集版本、验收标准、责任人、结果记录和失败处置方式写入发布记录；具体数值由组织基于风险和自身基线制定。

**阶段 A：离线准入。** 建立可重复的数据集，覆盖代表性任务、边界条件、已知失败和安全风险场景；同时检查任务结果与执行过程，并与当前基线比较。失败案例应可复现、可归因。安全或合规阻断类失败不得由其他维度的高分抵消。发布记录应注明数据集/判分规则版本、失败案例及处置结论；由指定的质量或风险责任人确认是否满足预先定义的准入标准。

**阶段 B：部署后 Smoke。** 在目标环境执行最小端到端请求，确认运行完成、响应可取得、关键工具/子步骤符合预期、追踪数据可用。测试前应记录预期响应、关键步骤和通过判据，测试后保存运行结果。关键链路失败、权限异常或追踪不可用时，不扩大流量；由发布责任人暂停推进并安排修复或升级风险评估。

**阶段 C：人工评审。** 对代表性输出、失败案例和边界轨迹进行有规范的复核，记录问题类型、严重性、阻断与否及处置结论。涉及敏感数据、高权限工具、重大业务影响或自动评判器不可靠时，应提高人工复核要求。组织应预先定义阻断问题分类、严重性标准、评审责任人和升级路径；例外审批须由明确的风险责任人书面批准并留痕，且不得把例外解释为来源规定或通用标准。抽样比例和评审一致性阈值由组织按风险制定。

**阶段 D：生产观察与扩量。** 扩大流量前确认关键追踪/监控信号、告警责任人、人工接管及回滚/降级路径可用；先受控观察，再依据组织预先定义的信号决定是否扩量。发布记录应列明观察窗口、信号阈值、响应责任人和停止/回滚动作。异常轨迹、用户反馈和人工复核问题应进入归因流程，并回灌离线回归集。敏感内容遵循最小必要记录和脱敏要求；若因此形成监控盲区，应明确记录并采用合规替代控制。

**发布决策采用分层、合取、不可抵消逻辑：**离线准入通过、Smoke 通过、人工评审无阻断问题、监控与回滚就绪、安全/合规阻断项为零，五项全部满足才进入下一阶段。任何一项失败都暂停推进；不能用其他项的高分抵消。阻断项的定义、判定责任和例外审批必须由组织事先确定并留痕。低风险、可逆变更可缩小人工评审范围，但不应省略基本离线回归、Smoke 和生产监控；高风险变更应加强人工复核和受控发布。

## 建议

1. **先按风险分级，再设组织自己的数值阈值。** 以业务影响、可逆性、权限范围和数据敏感度确定风险等级；再用自身基线和验证数据制定成功率、样本量、抽样比例、告警阈值及回滚时限。不要把本报告的定性门槛误读为已验证的通用数值。
2. **把结果、过程和安全分开记分。** 至少分别记录任务完成、工具调用/轨迹质量和安全/合规阻断项；对严重风险设置硬门槛，不以平均分掩盖低频高影响失败。
3. **将 Smoke 限定为部署健康检查。** Smoke 通过只说明所测路径可运行；质量、安全和业务适配仍需离线测试、人工评审及生产观察共同支持。
4. **建立可追溯的证据链。** 关联数据集版本、Agent/模型/工具配置、判分规则、人工评审结论、运行 trace 和发布版本，确保失败可复现、决策可审计。
5. **预先定义停止与恢复动作。** 明确哪些失败会阻止发布或扩量，谁负责告警响应，何时人工接管、降级或回滚；将线上问题转化为新的离线回归用例。

## 局限性

本轮核验的五个不同规范化页面来自四个机构：OpenAI Agent evals、Google Cloud agent evaluation、LangSmith Evaluation、LangSmith Observability 和 Microsoft Learn 的 Agent tracing 页面。OpenAI 页面抓取内容不完整，Google Cloud 页面主要呈现评估流程；未取得 LangSmith Online evaluations 专页或 NIST AI RMF Playbook Measure/Manage 的可验证页面，因此不据此声称其具体在线评估配置或治理要求。Microsoft 页面适用于 Foundry classic，且标注为 preview 并不建议用于生产工作负载，不能泛化为所有 Azure Agent 产品的生产承诺。

现有来源没有提供统一的离线通过率、数据集规模、Smoke 请求数、人工抽样比例、评审一致性阈值、告警阈值或回滚时限。Smoke 定义、人工评审流程和分层合取门槛均为基于证据形成的实施建议，不是官方标准。实际效果仍取决于测试集代表性、判分器有效性、风险分级、遥测完整性、隐私约束和组织响应能力。
