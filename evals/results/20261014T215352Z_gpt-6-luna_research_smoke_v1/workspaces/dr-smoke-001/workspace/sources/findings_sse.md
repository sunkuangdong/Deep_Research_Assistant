# Findings: Server-Sent Events (SSE) for Streaming LLM Responses

## Research scope
This note covers the SSE protocol and browser `EventSource` behavior relevant to delivering streamed LLM responses: event framing, unidirectional transport, reconnection and `Last-Event-ID`, browser constraints, and operational implications supported by standards or official documentation. It does not assess LLM application architecture or compare streaming protocols.

## Key findings
- **SSE is a UTF-8 text event stream, not arbitrary chunk framing.** The stream uses `text/event-stream`; lines are separated by LF, CRLF, or CR. A blank line dispatches the accumulated event. Fields include `data`, `event`, `id`, and `retry`; comments begin with `:` and can be used as keep-alive comments. Multiple `data:` lines are joined with newline characters. For LLM output, clients should parse complete SSE events rather than assume each network read or HTTP chunk corresponds to one model token or one event.
  Source: [WHATWG HTML Living Standard — Server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html)
- **The browser API is one-way.** `EventSource` receives events from a server; it does not provide a way to send application data back over that same event stream. A client can separately make requests (for example, ordinary HTTP requests) if it needs to submit prompts or control messages. The WHATWG standard defines an event source as a connection for receiving events, and MDN describes SSE as a unidirectional server-to-client connection.
  Sources: [WHATWG HTML Living Standard](https://html.spec.whatwg.org/multipage/server-sent-events.html), [MDN: Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)
- **Reconnection is built into `EventSource`.** When a connection closes, the browser may reconnect after a delay; the `retry:` field can set the reconnection time in milliseconds when its value is valid. An `id:` field updates the event stream’s last-event-ID string. On reconnection, the user agent sends that value in the `Last-Event-ID` request header, allowing an application to resume or deduplicate from an event identifier if its server implements that behavior. This mechanism does not itself guarantee replay, exactly-once delivery, or application-level recovery; those depend on server state and event-ID semantics.
  Source: [WHATWG HTML Living Standard — reconnection and event IDs](https://html.spec.whatwg.org/multipage/server-sent-events.html)
- **Browser API constraints matter for LLM streams.** Native `EventSource` accepts a URL and optional `withCredentials` setting, but does not expose a general request method/body or arbitrary request-header configuration. Consequently, it is not directly suited to sending a prompt in a POST body or attaching arbitrary authorization headers; applications commonly need a separate request pattern or a fetch-based streaming client when those are required. Cross-origin use is subject to CORS; credentials are opt-in through `withCredentials` for cross-origin requests. MDN also documents a low per-browser/per-domain connection limit for HTTP/1.1 (commonly six, browser-dependent); HTTP/2 negotiates a concurrent-stream limit, with MDN citing a default of 100. These limits can affect applications opening many simultaneous streams.
  Sources: [MDN: EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource), [MDN: Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)
- **Operationally, preserve streaming semantics end to end.** The standard specifies event-stream parsing and reconnection, but does not guarantee that intermediaries or application servers will flush each event promptly. For interactive LLM output, deployment should be tested through the actual proxy/CDN/server path for buffering, idle timeouts, and connection closure behavior. SSE comments can provide periodic bytes without dispatching an application event, but the standard does not prescribe a universal heartbeat interval or guarantee that comments defeat every intermediary timeout. Treat these as deployment-specific checks, not protocol guarantees.
  Sources: [WHATWG HTML Living Standard](https://html.spec.whatwg.org/multipage/server-sent-events.html), [MDN: Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)

## Evidence and uncertainty
The primary protocol claims are grounded in the WHATWG HTML Living Standard; browser API behavior and documented connection constraints are grounded in MDN. Search service calls failed due to quota (HTTP 403), so sources were identified from established official documentation URLs rather than verified through live search results in this run. The exact browser connection limits are implementation-dependent and may change; MDN explicitly frames HTTP/1.1 limits as browser-dependent. Buffering, flushing, and timeout behavior depend on infrastructure and are not guaranteed by SSE itself. `Last-Event-ID` provides a resume signal, not a guarantee that the server retains or replays prior events.
